## Kafka Fundamentals

### What Is Kafka? What Are Its Main Use Cases?

Kafka is a distributed streaming platform. What does that actually mean?

A streaming platform has three key capabilities:

1. **Message Queue**: Publish and subscribe to streams of messages—this capability is similar to a message queue, which is also why Kafka is categorized as one.
2. **Fault-Tolerant Durable Storage of Message Record Streams**: Kafka persists messages to disk, effectively eliminating the risk of message loss.
3. **Stream Processing Platform**: Process message streams as they are published; Kafka provides a complete stream-processing library.

Kafka has two primary use cases:

1. **Message Queue**: Building real-time streaming data pipelines to reliably move data between systems or applications.
2. **Data Processing**: Building real-time streaming applications that transform or process data streams.

### Compared to Other Message Queues, What Are Kafka's Advantages?

Whenever we talk about Kafka today, we tend to take it for granted that it is a stellar message queue, and we frequently compare it against RocketMQ and RabbitMQ. In my view, Kafka's main advantages over other message queues are as follows:

1. **Extreme Performance**: Built on Scala and Java, its architecture makes extensive use of batching and asynchronous processing, capable of handling tens of millions of messages per second at peak throughput.
2. **Unmatched Ecosystem Compatibility**: Kafka's compatibility with surrounding ecosystems is second to none, especially in the big data and stream computing domains.

In fact, in its early days, Kafka was not a qualified message queue at all—early Kafka was like a ragged child in the messaging world, lacking complete features and suffering from issues like message loss and no reliability guarantees. Of course, that had a lot to do with LinkedIn originally building Kafka to process massive volumes of logs—haha, it wasn't even designed to be a message queue in the first place, yet unexpectedly ended up carving out a prominent place in the message queue landscape.

Over subsequent releases, Kafka gradually addressed and fixed those shortcomings. Therefore, **the claim that "Kafka is unreliable as a message queue" is outdated!**

### Are You Familiar with the Queue Model? Do You Know Kafka's Messaging Model?

> Side note: Early standards like JMS and AMQP were established by authoritative organizations in the messaging domain, which I introduced in my [JavaGuide](https://github.com/Snailclimb/JavaGuide) article ["Message Queues Are Actually Very Simple"](https://github.com/Snailclimb/JavaGuide#%E6%95%B0%E6%8D%AE%E9%80%9A%E4%BF%A1%E4%B8%AD%E9%97%B4%E4%BB%B6). However, the evolution of these standards could not keep pace with how rapidly message queues evolved, so they are effectively deprecated today. As a result, different message queues often implement their own messaging models.

#### Queue Model: The Early Messaging Model

![Queue Model](/media/jg/ext/oss.javaguide.cn/javaguide/high-performance/message-queue/23-109f70ce.png)

**Uses a Queue as the message communication carrier under the Producer-Consumer pattern: each message can only be consumed by a single consumer, and unconsumed messages remain in the queue until consumed or expired.** For example, if a producer sends 100 messages and two consumers read from the queue, under normal circumstances each consumer will consume half in the order messages were sent (essentially taking turns, one for you, one for me).

**Problems with the Queue Model:**

Suppose we have a scenario where we need to distribute messages generated by a producer to multiple consumers, and *every* consumer must receive the *complete* message content.

The Queue Model handles this poorly. Some nitpickers might say: "We can just create a separate queue for each consumer and have the producer send multiple copies." That is a very foolish approach—not only does it waste resources, it also defeats the purpose of using a message queue in the first place.

#### Publish-Subscribe Model: Kafka's Messaging Model

The Publish-Subscribe model was designed primarily to solve the limitations of the Queue Model.

![Publish-Subscribe Model](/media/jg/ext/oss.javaguide.cn/java-guide-blog/.png-4648478c.png)

The Publish-Subscribe (Pub-Sub) model uses a **Topic** as the message communication carrier, similar to a **broadcast mode**: a publisher publishes a message, which is delivered through the Topic to all subscribers, **and users who subscribe after a message has already been broadcast will not receive that message.**

**In the Publish-Subscribe model, if there is only a single subscriber, it behaves essentially the same as the Queue Model. Therefore, functionally, the Publish-Subscribe model is compatible with the Queue Model.**

**Kafka adopts the Publish-Subscribe model.**

> **RocketMQ's messaging model is essentially identical to Kafka's. The only difference is that Kafka does not have the concept of a Queue—its counterpart is a Partition.**

## Kafka Core Concepts

### What Are Producer, Consumer, Broker, Topic, and Partition?

Kafka sends messages published by producers into a **Topic**, and consumers that need those messages can subscribe to the **Topic**, as illustrated below:

![](/media/jg/ext/oss.javaguide.cn/github/javaguide/high-performance/message-queue20210507200944439-3f714d95.png)

The diagram above introduces several key concepts in Kafka:

1. **Producer**: The party that produces messages.
2. **Consumer**: The party that consumes messages.
3. **Broker**: Can be thought of as an independent Kafka instance. Multiple Kafka Brokers form a Kafka Cluster.

At the same time, you have surely noticed that each Broker also contains two important concepts—Topic and Partition:

- **Topic**: Producers send messages to a specific Topic, and Consumers subscribe to a specific Topic to consume messages.
- **Partition**: A Partition belongs to a Topic. A Topic can have multiple Partitions, and Partitions under the same Topic can be distributed across different Brokers—which means a single Topic can span multiple Brokers, just as shown in the diagram above.

> Key takeaway: **A Partition in Kafka effectively corresponds to a Queue in a traditional message queue. Doesn't that make it much easier to understand?**

### Are You Familiar with Kafka's Multi-Replica Mechanism? What Benefits Does It Bring?

Another important aspect is that Kafka introduces a multi-replica (`Replica`) mechanism for Partitions. Among the multiple replicas of a Partition, one is designated as the **leader**, while the others are called **followers**. Messages we send are written to the leader replica, and follower replicas pull messages from the leader replica to synchronize.

> Producers and consumers interact only with the leader replica. You can think of the other replicas simply as copies of the leader replica whose sole purpose is to guarantee message storage safety. When the leader replica fails, a new leader is elected from the followers; however, any follower whose synchronization state lags behind the leader cannot participate in the leader election.

**What are the benefits of Kafka's multi-Partition and multi-Replica mechanism?**

1. By assigning multiple Partitions to a specific Topic and distributing those Partitions across different Brokers, Kafka achieves strong concurrency capability (load balancing).
2. Specifying a `Replica` count for Partitions greatly enhances message storage durability and disaster tolerance, though it correspondingly increases storage space requirements.

## Message Ordering, Message Loss, and Duplicate Consumption in Kafka

### How Does Kafka Guarantee Message Consumption Order?

When using message queues, we frequently encounter business scenarios that require strict message consumption ordering. For example, suppose we send two messages simultaneously, corresponding to the following two database operations:

1. Upgrade a user's membership tier.
2. Calculate the order price based on the membership tier.

If these two messages are consumed out of order, the final result will be completely wrong.

We know that a Partition in Kafka is where messages are actually stored—every message we send is placed into a Partition. Meanwhile, Partitions belong to a Topic, and we can configure multiple Partitions for a given Topic.

![](/media/jg/ext/oss.javaguide.cn/javaguide/high-performance/message-queue/KafkaTopicPartionsLayout-b39911ea.png)

Every time a message is added to a Partition, it is appended to the tail, as shown above. **Kafka can only guarantee message ordering within a Partition.**

> When a message is appended to a Partition, it is assigned a specific offset. Kafka guarantees message ordering within a partition via offsets.

Accordingly, there is a very simple way to guarantee consumption order: **map 1 Topic to only 1 Partition**. That certainly solves the problem, but it defeats Kafka's core parallel design.

When sending a message in Kafka, you can specify four parameters: `topic`, `partition`, `key`, and `data`. If you explicitly specify a `Partition` when sending, all such messages are sent to that Partition. Moreover, messages with the same `key` are guaranteed to be routed to the same `partition`—we can use a table or entity `id` as the `key`.

To summarize, there are two ways to guarantee message consumption ordering in Kafka:

1. Map 1 Topic to only 1 Partition.
2. (Recommended) Specify a `key` or `Partition` when sending messages.

Of course, these are not the only two methods—they are simply the easiest to understand.

Two boundaries must also be kept in mind for ordered consumption:

- **Ordering is only guaranteed within the same partition**: multiple partitions naturally execute in parallel and do not guarantee global ordering.
- **Failure retries can break business-level ordering**: if one message fails to process while subsequent messages have already been processed, the business layer still needs a state machine or version number as a safeguard.

Therefore, production systems typically combine "same business key routed to the same partition + sequential consumption within a single partition + consumer-side idempotency / state-machine validation."

Additionally, it is recommended to set a reasonable value for the Producer's `retries` parameter—typically 3, though set higher if preventing message loss is critical. Once configured, the Producer automatically retries when network issues occur, avoiding message loss. It is also advisable to configure a retry backoff interval; if the interval is too short, retries have little effect because a brief network blip will burn through all 3 attempts instantaneously.

#### Message Loss on the Consumer Side

We know that when messages are appended to a Partition, each receives a specific offset. The offset indicates the Consumer's current position in that Partition. Kafka guarantees message ordering within a partition via offsets.

![kafka offset](/media/jg/ext/oss.javaguide.cn/javaguide/high-performance/message-queue/kafka-offset-c3444a1d.jpg)

After a consumer polls a message from a partition, it automatically commits the offset. Auto-committing creates a pitfall: imagine a consumer receives a message and is just about to process it when it suddenly crashes—the message was never actually processed, yet its offset has already been committed.

**The blunt fix is to disable auto-commit and manually commit the offset only after the message has truly been processed.** However, attentive readers will immediately notice that this introduces duplicate consumption: if you crash right after processing the message but before committing the offset, that message will theoretically be consumed twice.

#### When Kafka Itself Loses Messages

We know Kafka introduces a multi-replica (`Replica`) mechanism for Partitions. Among a Partition's replicas, one is the leader and the others are followers. Messages are sent to the leader replica, and follower replicas pull messages from the leader to sync. Producers and consumers interact solely with the leader replica; other replicas are copies solely for message storage safety.

**Consider this scenario: if the broker hosting the leader replica suddenly crashes, a new leader must be elected from the follower replicas; however, if the leader still held data that had not yet been synchronized to the followers, message loss will occur.**

**Set `acks = all`**

The solution is to configure **`acks = all`**. `acks` is a critical parameter for a Kafka Producer.

The default value of `acks` is `1`, meaning a send is considered successful as soon as the leader replica receives the message. When we set **`acks = all`**, the producer only receives a success acknowledgment from the server after *all* replicas in the ISR list have received the message. This is the highest and safest durability mode, ensuring more than one Broker has received the message, though it incurs higher latency.

**Set `replication.factor >= 3`**

To ensure the leader replica has follower replicas available to sync messages, we typically configure **`replication.factor >= 3`** for a topic. This guarantees every partition has at least 3 replicas. While it introduces storage redundancy, it delivers data safety.

**Set `min.insync.replicas > 1`**

In general, we also need to set **`min.insync.replicas > 1`**, which requires a message to be written to at least 2 replicas before being considered successfully sent. The default value of **`min.insync.replicas`** is `1`, which should be avoided in production.

However, to preserve high availability across the Kafka cluster, you must ensure **`replication.factor > min.insync.replicas`**. Why? Suppose they are equal: if even a single replica goes down, the entire partition stops accepting writes, clearly violating high availability! It is generally recommended to configure **`replication.factor = min.insync.replicas + 1`**.

**Set `unclean.leader.election.enable = false`**

> **Starting from Kafka 0.11.0.0, the default value of `unclean.leader.election.enable` changed from `true` to `false`.**

As noted earlier, messages are written to the leader replica and pulled by followers to sync. Synchronization progress varies across follower replicas. When **`unclean.leader.election.enable = false`** is configured, if the leader replica fails, Kafka will not elect a new leader from followers that have not adequately caught up with the leader, thereby reducing the likelihood of message loss.

In production environments, it is also recommended to pay attention to these Producer-side configurations:

- Enable the idempotent producer to prevent producer retries from writing duplicate messages into the same partition.
- Properly tune `delivery.timeout.ms`, `request.timeout.ms`, and `linger.ms` to balance reliability, latency, and throughput.
- Record send-failure logs or use a local message table for critical business messages to facilitate subsequent compensation.

Kafka's reliability is not determined by any single parameter; rather, it is jointly guaranteed by Topic replicas, ISR, Producer ACK, Consumer offset commit timing, and business-level idempotency.

### How Does Kafka Prevent Duplicate Message Consumption?

**Root causes of duplicate message consumption in Kafka:**

- Data was already processed on the consumer/service side, but the offset failed to commit (the root cause).
- Long business processing times or network issues lead Kafka to assume the consumer service is dead, triggering a partition rebalance.

**Solutions:**

- Implement idempotency checks in the consumer service—for example, leveraging natural idempotency mechanisms such as Redis `SET` or MySQL primary keys. This is the most effective approach.
- Set **`enable.auto.commit`** to `false` to disable auto-commit and manually commit offsets in application code. This raises a question: **When is the right time to commit the offset?**
  - Commit after processing the message: still carries the risk of duplicate consumption, just like auto-commit.
  - Commit immediately upon polling the message: carries the risk of message loss. Scenarios that tolerate latency often adopt this approach and run scheduled jobs during off-peak hours (e.g., early morning) for data reconciliation.

## What Are the Risks of Rebalance? How Can Its Impact Be Reduced?

Changes in the number of consumers in a Consumer Group, changes in subscribed Topics, or a consumer failing to send heartbeats for an extended period can all trigger a Rebalance. During a Rebalance, partitions are reassigned and some consumers pause consumption; in severe cases, this causes consumption jitter and duplicate consumption.

Common optimization strategies:

- Avoid frequent scaling or restarts of consumer instances; use rolling, batched deployments during releases.
- Configure `max.poll.interval.ms` appropriately so long-running batch processing does not cause a consumer to be kicked out of the group.
- Limit the number of messages fetched per poll to prevent processing time from exceeding the heartbeat or poll interval.
- Use static group membership or smoother partition assignment strategies to reduce unnecessary partition migrations.
- Make the consumer idempotent, because duplicates can still occur between offset commits and business processing before or after a Rebalance.

In an interview, if asked about Rebalance, don't stop at saying "consumers reassign partitions." More importantly, explain clearly that it introduces brief consumption pauses and duplicate consumption risks, and describe how configuration tuning, deployment strategies, and idempotent design minimize its impact.

## Kafka Retry Mechanism

When discussing how Kafka prevents message loss, we mentioned Kafka's retry mechanism. Because this topic is quite important, let's examine it in detail here.

Many online articles about Spring Kafka's default retry mechanism are outdated and behave completely differently from actual runtime behavior. Below is a fresh walkthrough based on the source code of [spring-kafka-2.9.3](https://mvnrepository.com/artifact/org.springframework.kafka/spring-kafka/2.9.3).

### What Happens When Consumption Fails?

During consumption, if an exception occurs while processing one message, does it block subsequent messages in the partition/queue and stall the business?

Producer code:

```Java
 for (int i = 0; i < 10; i++) {
   kafkaTemplate.send(KafkaConst.TEST_TOPIC, String.valueOf(i))
 }
```

Consumer code:

```Java
   @KafkaListener(topics = {KafkaConst.TEST_TOPIC},groupId = "apple")
   private void customer(String message) throws InterruptedException {
       log.info("kafka customer:{}",message);
       Integer n = Integer.parseInt(message);
       if (n%5==0){
           throw new  RuntimeException();
       }
   }
```

Under the default configuration, when consumption throws an exception, Kafka retries the message; after multiple retries, it skips the current message and proceeds to consume subsequent messages without blocking on the failing message indefinitely. Below is a consumption log excerpt showing that `test-0@95` is skipped after multiple retries:

Therefore, even if a particular message fails to be consumed, the Kafka consumer can still continue processing subsequent messages without getting stuck forever, ensuring normal business continuity.

### How Many Times Does It Retry by Default?

Under the default configuration, consumption exceptions trigger retries—how many times does it retry, and is there a delay interval between retries?

Inspecting the source code, the `FailedRecordTracker` class has a `recovered` method that returns a `boolean` indicating whether retries should stop or continue. Below is the retry decision logic inside that method:

```java

```

Here, `BackOffExecution.STOP` has a value of `-1`.

```java
@FunctionalInterface
public interface BackOffExecution {

	long STOP = -1;
	long nextBackOff();

}
```

`nextBackOff` invokes the `nextBackOff()` method on the `BackOff` implementation. If the current attempt count exceeds the maximum attempts, it returns `STOP`—that is, retries stop only after exceeding this maximum execution count.

```Java
public long nextBackOff() {
  this.currentAttempts++;
  if (this.currentAttempts <= getMaxAttempts()) {
    return getInterval();
  }
  else {
    return STOP;
  }
}
```

What is the value of `getMaxAttempts`? Tracing back to the beginning, when an exception occurs it enters `DefaultErrorHandler`. The default constructor of `DefaultErrorHandler` is:

```Java
public DefaultErrorHandler() {
  this(null, SeekUtils.DEFAULT_BACK_OFF);
}
```

`SeekUtils.DEFAULT_BACK_OFF` is defined as:

```Java
public static final int DEFAULT_MAX_FAILURES = 10;

public static final FixedBackOff DEFAULT_BACK_OFF = new FixedBackOff(0, DEFAULT_MAX_FAILURES - 1);
```

The value of `DEFAULT_MAX_FAILURES` is `10`, and `currentAttempts` runs from `0` to `9`, so it executes 10 times in total with a retry interval of `0`.

Finally, to summarize briefly: under the default configuration, a Kafka consumer performs at most 10 attempts with a retry interval of 0—meaning immediate retries. If the message still cannot be consumed successfully after those 10 attempts, retrying stops and the message is treated as a consumption failure.

### How to Customize Retry Count and Retry Interval?

As seen in the code above, the default error handler's retry count and interval are controlled by `FixedBackOff`, which is the default when initializing `DefaultErrorHandler`. Therefore, to customize the retry count and interval, you simply pass a custom `FixedBackOff` when initializing `DefaultErrorHandler`. Re-implement a `KafkaListenerContainerFactory` bean and call `setCommonErrorHandler` to set your custom error handler.

```Java
@Bean
public KafkaListenerContainerFactory kafkaListenerContainerFactory(ConsumerFactory<String, String> consumerFactory) {
    ConcurrentKafkaListenerContainerFactory factory = new ConcurrentKafkaListenerContainerFactory();
    // Customize retry interval and attempt count
    FixedBackOff fixedBackOff = new FixedBackOff(1000, 5);
    factory.setCommonErrorHandler(new DefaultErrorHandler(fixedBackOff));
    factory.setConsumerFactory(consumerFactory);
    return factory;
}
```

### How to Trigger Alerts After Retries Fail?

Custom post-retry-failure logic must be implemented manually. Below is a simple example that overrides `DefaultErrorHandler`'s `handleRemaining` method to add custom alerting and other actions:

```Java
@Slf4j
public class DelErrorHandler extends DefaultErrorHandler {

    public DelErrorHandler(FixedBackOff backOff) {
        super(null,backOff);
    }

    @Override
    public void handleRemaining(Exception thrownException, List<ConsumerRecord<?, ?>> records, Consumer<?, ?> consumer, MessageListenerContainer container) {
        super.handleRemaining(thrownException, records, consumer, container);
        log.info("重试多次失败");
        // Custom actions
    }
}
```

`DefaultErrorHandler` is just one built-in error handler; Spring Kafka also provides the `CommonErrorHandler` interface. Implementing `CommonErrorHandler` manually gives you high flexibility for custom behavior—for instance, applying different retry strategies and business logic depending on the exception type.

### How to Reprocess Messages After Retries Exhaust?

Once the maximum retry count is reached, the failing message is skipped directly and consumption moves forward. After the code bug is fixed, how can we reprocess those failed messages?

A **Dead Letter Queue (DLQ)** is a special queue in message-oriented middleware. It is primarily used to handle messages that cannot be processed properly by consumers—typically messages that would otherwise be "discarded" or "dead" due to malformed formats, processing failures, or consumption timeouts. When a message enters the queue, consumers attempt to process it. If processing fails or still fails after exceeding a certain number of retries, the message can be routed to a Dead Letter Queue instead of being permanently discarded. In the DLQ, these unprocessable messages can be further analyzed and handled to diagnose root causes, fix bugs, and take appropriate remediation steps.

`@RetryableTopic` is an annotation in Spring Kafka used to configure retry support for a Topic, and using this annotation is the more recommended way to implement retries.

```Java
// Retry 5 times, with an initial interval of 100 ms and a max interval of 1 second
@RetryableTopic(
        attempts = "5",
        backoff = @Backoff(delay = 100, maxDelay = 1000)
)
@KafkaListener(topics = {KafkaConst.TEST_TOPIC}, groupId = "apple")
private void customer(String message) {
    log.info("kafka customer:{}", message);
    Integer n = Integer.parseInt(message);
    if (n % 5 == 0) {
        throw new RuntimeException();
    }
    System.out.println(n);
}
```

When the maximum number of retries is reached and the message still fails to process, it is sent to the corresponding Dead Letter Queue (DLQ). To handle messages in the Dead Letter Queue, you can either use `@DltHandler` or re-consume them using `@KafkaListener`.
