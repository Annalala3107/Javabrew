Transitioning from user mode to kernel mode during a system call is merely the starting point for understanding this execution path. Following a single `read()` call deeper, you encounter several closely interrelated questions:

- How does `read()` actually enter the kernel?
- Why can a timer interrupt halt a currently running thread?
- Why is a Page Fault sometimes normal behavior, but other times turns into `SIGSEGV`?
- When a system call enters the kernel, does a thread context switch necessarily occur?

These questions can be tied together through an invocation of `read(fd, buf, count)`. The user application invokes `read()`, glibc places the system call number and parameters into designated registers, and the CPU executes `syscall` to enter the kernel. The kernel inspects the file descriptor (fd), buffer address, and file status, then decides whether to retrieve data from the Page Cache, file system, socket receive buffer, or device driver.

If the data is already prepared, the kernel copies it back to the user buffer, and `read()` returns quickly. If the data is not yet ready, the current thread may go to sleep; once the disk I/O completes or the network card receives the packets, a hardware interrupt arrives in the kernel, and the kernel wakes up the thread from the wait queue. Only after the thread is scheduled onto a CPU again does `read()` resume and return.

Once a standard I/O operation begins running, system calls, interrupts, exceptions, and scheduling are often chained together.

## Categories of Events Entering the Kernel

Under normal circumstances, when the CPU executes user programs, the next instruction is determined by the program counter and branching logic. Peripheral events, errors in the current instruction, or user programs actively requesting kernel services will all transfer control flow to the kernel. CSAPP terms these deviations from the normal instruction stream as Exceptional Control Flow (ECF), classifying interrupts, traps, faults, and aborts as distinct types.

Common entry points can be grouped by source:

- **Interrupt**: Originates from external hardware and is completely independent of the current instruction. Network card packet arrivals, disk I/O completions, and timer expirations all fall into this category.
- **Trap**: The program actively executes a special instruction to enter the kernel. System calls are the most common traps.
- **Fault**: An issue encountered while executing the current instruction that the kernel might be able to repair. A classic example is a page fault; once repaired, the CPU re-executes the instruction that originally triggered the fault.
- **Abort**: The processor detects an unrecoverable severe hardware/system error and typically never returns to the original instruction stream.

![Diagram of relationships between interrupts, exceptions, and system calls](/media/jg/ext/oss.javaguide.cn/javaguide/cs-basics/operating-system/ecf-kernel-entry-map-05ab14c5.webp)

The term `trap` is used with slight variations across different references. In the context of CSAPP, it usually refers to a synchronous exception actively triggered by a program, such as a system call; RISC-V, on the other hand, defines a trap as any transfer of control caused by an exception or interrupt. When this article mentions "trap / system call", it uses the former narrow definition; RISC-V-specific contexts will be called out separately.

## Relationships Between Interrupts, Exceptions, System Calls, and Signals

These terms are easy to confuse because they operate at different layers of abstraction.

Hardware interrupts, synchronous exceptions, and system calls describe *why* the CPU enters the kernel; signals, however, are software notifications delivered by the kernel to a process or thread. A signal may be translated from a hardware exception, or generated by another process, a terminal, or a timer.

Let us summarize these concepts in a comparison table:

| Concept | Trigger Source | Synchronous / Asynchronous | Handler | Typical Outcome |
| --- | --- | --- | --- | --- |
| Hardware Interrupt | Peripherals or timers | Asynchronous | Kernel interrupt handler | Processes device events, wakes waiting tasks, triggers scheduling |
| Synchronous Exception | Execution of the current instruction | Synchronous | Kernel exception handler | Retries after fix, converts to signal, or terminates process |
| System Call | Traps actively triggered by user programs via `syscall`/`ecall` | Synchronous | Kernel system call entry | Returns result, returns error code, or blocks waiting for resources |
| Signal | Notifications sent by kernel or processes | Typically asynchronous (can be triggered synchronously by exceptions) | Target process default action or user-mode signal handler | Ignored, terminated, suspended, continued, or handler executed |

Synchronous vs. asynchronous in this table looks at whether the event is directly caused by the current instruction. Division by zero, illegal instructions, Page Faults, and system calls are all directly tied to the instruction currently being executed, making them synchronous events. Hardware interrupts originate from external devices or timers: while the CPU is busy running your Java thread, the network interface card (NIC) might simultaneously receive a packet; this occurrence is entirely unrelated to the current line of user code, making it an asynchronous event.

Blocking vs. non-blocking represents another dimension. Entering the kernel via `read()` is synchronous, but once inside the kernel, if data is not yet ready, a blocking fd will put the thread to sleep; an fd configured with `O_NONBLOCK` may return `EAGAIN` immediately.

A hardware interrupt is like a peripheral tapping the CPU on the shoulder. For example, while the CPU is executing your Java thread, a timer interrupt arrives; once the CPU completes the current instruction, it vectors into the kernel's interrupt entry point. The kernel updates the clock, accounts for runtime, and if necessary, instructs the scheduler to hand the CPU over to another thread. You never wrote any code to yield the CPU, yet the thread can still be preempted.

An exception stems from the current instruction itself. Dividing by 0, executing an illegal opcode, or accessing an unauthorized memory address are all issues triggered by that specific instruction. Page Faults also belong to this category: when a process accesses a virtual address for which the page table currently lacks a valid mapping, the CPU must hand the context over to the kernel. A synchronous exception does not guarantee it can be fixed; if the kernel cannot resolve it, it delivers a signal or terminates the process.

A system call is a user program actively asking the kernel for assistance. User-space programs cannot directly read disks, modify page tables, or manipulate network hardware, so glibc functions like `read()`, `write()`, `fork()`, and `mmap()` ultimately dispatch through system call interfaces provided by the kernel.

Signals do not belong to the CPU hardware entry mechanism. They are notifications delivered by the kernel to a process or thread. An illegal memory access might initially trigger a Page Fault; when the kernel discovers it cannot fix the fault, it delivers `SIGSEGV` to the process. When a user presses `Ctrl+C`, the terminal driver causes the kernel to send `SIGINT` to the foreground process group. Another process can also send signals by invoking `kill()`.

These distinct dimensions can be disentangled as follows:

| Dimension | Core Question | Example |
| --- | --- | --- |
| Synchronous / Asynchronous Event | Is the event triggered directly by the current instruction? | Page Fault is a synchronous exception; NIC interrupt is an asynchronous interrupt |
| Blocking / Non-blocking I/O | Does the thread wait when resources are not ready? | Blocking `read()` sleeps; non-blocking `read()` returns `EAGAIN` |
| User-mode / Kernel-mode Switch | Does CPU enter kernel to execute privileged code? | `syscall`, Page Fault, and hardware interrupts all enter the kernel |
| Thread Context Switch | Does CPU switch from one thread to another? | May occur upon blocking, preemption, or rescheduling |

A signal handler is not a kernel function either. The kernel typically inspects pending signals right before returning from kernel mode to user mode; if a handler needs to be executed, it sets up the user stack, registers, and a trampoline, then directs the thread back to user space to execute the handler. Thus, a signal handler does not arbitrarily insert itself between random machine instructions; it executes after the thread returns from kernel mode to user space, or after it wakes from interruptible sleep, as arranged by the kernel. In multithreaded programs, note that a signal sent to a process is not necessarily handled by the thread you expect; the kernel selects an arbitrary thread that does not have that signal masked.

Where control returns after handling the event also varies:

| Type | Typical Return Destination After Handling |
| --- | --- |
| Interrupt | Returns to the interrupted location to continue execution, or schedules another thread |
| Trap / System Call | Typically returns to the instruction immediately following the trap; exceptions include syscall restart |
| Fault / Page Fault | Re-executes the instruction that originally triggered the fault after repairing |
| Abort | Typically does not return to the original program |

This table describes only the most common paths. In real-world systems, the kernel may also deliver signals, restart system calls, switch to another thread, or terminate the process outright.

## User-Mode/Kernel-Mode Switching vs. Context Switching

The difference between user mode and kernel mode lies in CPU privilege levels. User mode cannot execute privileged instructions or freely access kernel address space; kernel mode can manage page tables, hardware devices, interrupt controllers, and schedulers.

Transitioning from user mode to kernel mode is not a regular function call. The CPU and kernel must preserve sufficient execution state; otherwise, they would not know which instruction in the user program to return to later.

On x86-64, 64-bit system calls typically use the `syscall` instruction; exceptions and external interrupts mostly enter through entry points configured in the IDT (Interrupt Descriptor Table). Some exceptions push an error code onto the stack, while others do not; special entry points like NMI and Double Fault may even use dedicated IST (Interrupt Stack Table) stacks.

This article uses Linux x86-64 as an example, so it focuses on `syscall`. Other architectures or legacy ABIs may use entry instructions like `int 0x80`, `sysenter`, `ecall`, or `svc`, each with distinct register conventions.

The `syscall` instruction itself does very limited work. It saves the return address and flags register into `RCX` and `R11`, but does not save the full register context like a normal function call, nor does it automatically switch to the kernel stack. Linux entry assembly must continue the sequence by switching stacks, executing `swapgs`, saving registers, and so on.

It is equally essential to distinguish between a mode switch and a context switch:

- User-mode / Kernel-mode switch: The CPU transitions from a low privilege level to a high privilege level, executes kernel code, and returns to user mode.
- Context switch: The scheduler switches the CPU from one thread or process to another execution entity.

A system call definitely enters the kernel, but it does not necessarily switch to another thread. Calls like `getpid()` generally return almost immediately, and the current thread continues running. If `read()` must wait for data, the kernel may suspend the current thread and schedule another thread instead. Additionally, certain time-related interfaces can be completed entirely in user space via vDSO; for instance, `clock_gettime()` and `gettimeofday()` on certain architectures and configurations can read kernel data pages mapped into user space, without genuinely entering the kernel every time.

## The System Call Path of `read()`

Taking `read(fd, buf, count)` on Linux x86-64 as an example, application code normally calls the glibc wrapper function rather than writing raw assembly.

![read system call flowchart](/media/jg/ext/oss.javaguide.cn/javaguide/cs-basics/operating-system/read-syscall-path-4aeb6736.webp)

glibc places the system call number into `rax` and the arguments into agreed-upon registers. On x86-64, system call arguments are placed in order into `rdi`, `rsi`, `rdx`, `r10`, `r8`, and `r9`.

After the CPU executes `syscall`, it jumps to the kernel-configured entry point per architectural convention. The Linux entry code saves the register states needed later, and dispatches to the corresponding handler for `read` based on the system call number. The kernel inspects the fd, access permissions, and other parameters; when copying data to the user buffer, address invalidity can still result in `EFAULT`.

When reading a regular file, the path traverses the VFS (Virtual File System) and the specific filesystem implementation, attempting to pull data from the Page Cache first. When reading a socket, the kernel checks whether the receive buffer has data. Once data is ready, the kernel copies it into the user-supplied `buf`.

When the kernel accesses a user buffer, it can also trigger a Page Fault. Linux records user memory access instructions that might fault inside an exception table; if a fault occurs at a recoverable location, the kernel jumps to the corresponding fixup code, converting the outcome into an error return like `-EFAULT`, rather than crashing the kernel.

For instance, if `buf` in `read()` points to an obviously unwritable address, the system call will not bring down the kernel; instead, it returns `-1` and sets `errno` to `EFAULT`.

```c
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    int fd = open("/dev/zero", O_RDONLY);
    char *p = (char *)1;
    ssize_t n = read(fd, p, 1); // n == -1, errno == EFAULT
    printf("n=%zd errno=%d\n", n, errno);
}
```

The description of `EFAULT` in `read(2)` states that the user buffer lies outside the accessible address space. In the kernel execution path, this occurs when copying data back to the user buffer. The x86 exception table documentation also uses `get_user()` as an example: instructions accessing user memory that may fault are paired with fixup code; once a Page Fault occurs, the kernel looks up this address pair, adjusts the return value to `-EFAULT`, and jumps to the fixup routine to clean up.

Upon returning from a system call, a successful `read()` returns the actual number of bytes read; this value can be smaller than `count` without being considered an error. On failure, the kernel returns a negative error code, which the glibc wrapper translates into `-1` while setting `errno`. If the user buffer is inaccessible, `EFAULT` may occur; if interrupted by a signal during blocking wait, `EINTR` may be returned.

In production code, never assume that a single `read()` will either fill the buffer completely or fail. During a blocking system call wait, if the thread receives a signal and executes its handler, the system call may return `EINTR`; if partial data was already read before the signal arrived, `read()` may return the bytes read so far rather than failing. If `SA_RESTART` was specified when installing the signal handler, certain blocking system calls will automatically restart after the handler returns. Whether restart occurs depends on the interface type and signal configuration.

## Timer Interrupts and Preemption

A preemptive operating system cannot rely on every program to voluntarily yield the CPU. Textbooks commonly simplify this mechanism to the kernel configuring a hardware timer that periodically fires interrupts. While modern Linux supports tickless mode and may not fire ticks at a fixed frequency, timer interrupts remain the foundational conceptual model for understanding preemption.

Suppose Thread A is running in user space. When the timer expires, the CPU enters the kernel's timer interrupt handler. The kernel updates Thread A's execution time and checks whether rescheduling is needed. If rescheduling is not required, execution returns to Thread A upon handler completion, and A continues running; if rescheduling is needed, the kernel saves Thread A's execution context, selects Thread B, switches to B's kernel stack and register context, and finally returns from the kernel to Thread B's user-space execution point.

When OSTEP introduces Limited Direct Execution, it describes this exact chain: a timer interrupt allows hardware and kernel to save the current process's user registers, the kernel invokes a switch routine to save the old process context and restore the new process context, and finally returns to the new process via return-from-trap.

An interrupt definitely occurred along this path; whether a context switch occurs depends on whether the scheduler chooses a different thread.

Hardware interrupt handlers must generally execute quickly and exit, and cannot block or sleep arbitrarily like standard process contexts. Heavier work is deferred to softirqs, workqueues, or kernel threads.

Packet reception by a network card is a classic example. The basic path of Linux NAPI is: the device first notifies the host via a hardware interrupt, the driver schedules NAPI inside the interrupt handler, and subsequent packet processing runs in the softirq context. Once the driver schedules NAPI, it typically keeps IRQs masked until NAPI polling concludes, because continuing to fire hardware interrupts during this phase is unnecessary. If packet processing volume is excessive or softirqs are delayed, dedicated kernel threads like `ksoftirqd` may take over. When you see `ksoftirqd` or `%si` persistently elevated in production, consider network packet volume, softirq pressure, and interrupt affinity. The hard interrupt merely enqueues the deferred work; batch processing of packets has already switched to the softirq or kernel thread context.

## Page Faults: Normal Paths vs. Error Paths

The name "Page Fault" easily leads people to assume a program error has occurred. In reality, it merely indicates that when the CPU performs address translation or permission checks, the current page table entry cannot satisfy the access directly.

Common scenarios include:

1. Physical memory has not yet been allocated to the page, such as when a lazily allocated heap page is accessed for the first time;
2. The page resides in a file or Swap space and is not currently resident in physical memory;
3. A copy-on-write (COW) page is written to, where the page table was temporarily marked read-only, requiring the kernel to duplicate it;
4. Access permissions are violated, such as user mode accessing kernel pages, writing to a read-only page, or executing a non-executable page;
5. The address does not belong to any valid virtual memory area (VMA) of the process.

![Page Fault handling branch flowchart](/media/jg/ext/oss.javaguide.cn/javaguide/cs-basics/operating-system/page-fault-branching-8bcbb8b0.webp)

When handling a Page Fault, the kernel first checks whether the faulting address falls within a valid VMA of the process, and then verifies whether the access type and permissions match.

A legitimate page fault can be repaired. The kernel allocates a physical page, reads the page from disk/file, swaps it in from Swap, or handles COW, and updates the page table before returning. The CPU then re-executes the instruction that originally triggered the exception. Such faults can be minor faults or major faults, the difference being whether physical I/O was required.

When an address does not belong to any valid VMA, or when the access violates page-level permissions, the kernel typically delivers `SIGSEGV` to the faulting thread. Accessing addresses near `NULL` or writing to read-only mappings are typical examples. In C/C++, out-of-bounds array access does not guarantee a Page Fault: if the target address still lands within a page that is mapped with permissible access rights, the program may simply corrupt adjacent data silently. Only when an out-of-bounds address hits an unmapped region or violates page permissions will the hardware hand the problem to the kernel via a Page Fault.

The COW `fork()` and lazy allocation mechanisms in xv6 illustrate this well. Parent and child processes initially share read-only pages; whichever process writes triggers a page fault, prompting the kernel to copy the page and let the write proceed. When a process expands its address space, the kernel can initially record only the range, allocating physical pages only upon first access. Both scenarios leverage Page Faults to defer work efficiently.

`userfaultfd(2)` provides an advanced example: after registering a memory range from user space, missing, minor, or write-protect page faults can become events on a file descriptor; the faulting thread blocks, while another user-space thread supplies the page, resolves the fault, or removes write protection before allowing it to proceed. This mechanism is frequently used in virtual machine live migration, lazy loading, and dirty page tracking, though general backend services rarely invoke it directly.

## The Cost of System Calls

System calls are significantly heavier than regular function calls. A normal function call remains in user space, passing parameters, saving necessary context, and branching/returning according to the ABI; a system call must switch to kernel mode, traverse entry assembly to save context, perform privilege checks, and potentially access page tables, file objects, device drivers, or wait queues. Before returning to user space, the kernel may also inspect pending signals, preemption flags, and rescheduling requirements.

However, the overhead of system calls cannot be generalized. Calls like `getpid()` spend most of their time in entering and exiting kernel mode; `read()` hitting disk I/O spends most of its time waiting for hardware and copying data. Locks built on `futex` typically perform only user-space atomic operations in the uncontended case, avoiding `futex(2)` calls; only when contention occurs and threads need to sleep or wake up does execution enter the kernel via `futex(2)`.

In engineering practice, never sacrifice correctness just to shave off a single system call. Common, practical optimizations center on batching and eliminating needless waits: buffered I/O, reading/writing larger chunks, I/O multiplexing, `sendfile()`, `mmap()`, and `io_uring`, each mitigating mode switching, data copying, or wait overhead across different workloads.

## Key Interview Takeaways

When asked "What is the relationship between interrupts, exceptions, and system calls?", frame your answer around entry sources:

> The CPU normally follows its instruction stream. Peripheral events, errors in the current instruction, or user programs requesting kernel services will cause control flow to enter the kernel. Hardware interrupts originate from external devices and are asynchronous; synchronous exceptions are triggered by the current instruction; system calls are traps actively initiated by programs via instructions like `syscall` or `ecall`, also qualifying as synchronous events. After handling, the kernel may return to the original program, schedule another thread, or deliver a signal to the process.

When asked about the "System call workflow", use `read()` as an anchor:

> A glibc wrapper function loads the system call number and arguments into agreed-upon registers, then executes `syscall`. The CPU branches to the kernel entry point according to architectural convention, where Linux entry code saves the register states needed later, dispatches to the corresponding handler based on the syscall number, verifies arguments and permissions, and executes VFS, network, or memory management logic. Upon return, the result is placed back into registers; on failure, glibc converts the negative error code into `-1` and sets `errno`. If the call must wait for I/O, the thread blocks, and subsequent device interrupts wake it up.

When asked about "The difference between Page Faults and illegal memory access", emphasize kernel triage:

> A Page Fault merely means the CPU could not complete address translation or permission checks using the current page table entry. The kernel determines whether the address and access permissions are valid. Legitimate page faults can be repaired—such as allocating anonymous pages, faulting in pages from files or Swap, or processing COW—after which the faulting instruction is re-executed; illegal accesses cannot be repaired and typically result in `SIGSEGV`, causing the process to terminate by default.

A user-mode/kernel-mode switch and a thread context switch are not the same thing. A true system call always enters the kernel, but the CPU only performs a thread switch when the scheduler selects a different execution entity—such as when the current thread blocks, voluntarily yields the CPU, or is preempted.
