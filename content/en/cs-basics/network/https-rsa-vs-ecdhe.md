When many people first learn about HTTPS, they are left with a very rough impression:

**HTTPS = HTTP + Encryption, Encryption = RSA. Therefore, HTTPS = RSA Encryption.**

This understanding didn't come out of nowhere. Early HTTPS deployments indeed heavily used RSA-related cipher suites, and many introductory tutorials loved to use RSA as the primary example.

Strictly speaking, however, HTTPS has never been equivalent to RSA encryption. Even in the era of TLS 1.0 and TLS 1.1, RSA was merely one of the available options, with key exchange methods like DHE also existing in the protocol. By TLS 1.3, static RSA key exchange had been completely removed, and RSA now primarily appears in certificate signing and identity authentication.

Therefore, what this article really aims to compare is not "which is more advanced, RSA or ECDHE".

**In an RSA handshake, session key material is generated by the client and sent encrypted to the server; in an ECDHE handshake, session key material is never directly transmitted across the wire, but is independently calculated by both the client and the server.**

This article primarily answers several questions:

1. Why is HTTPS not equivalent to RSA encryption?
2. How is session key material obtained in an RSA handshake versus an ECDHE handshake?
3. Why does ECDHE provide forward secrecy?
4. Why did TLS 1.3 remove static RSA key exchange?

Once these questions are clearly explained, concepts like `PreMasterSecret`, `Server Key Exchange`, forward secrecy, and the removal of static RSA in TLS 1.3 will all become intuitive to follow.

## Two Core Problems of the TLS Handshake

HTTPS continues to use HTTP semantics. In the TLS 1.2 scenario focused on in this article, HTTP messages are transmitted via TLS over TCP; HTTP/3, however, runs on QUIC with integrated TLS 1.3 and no longer uses TCP.

Once the handshake is completed, what truly protects application data is typically a symmetric encryption algorithm such as AES-GCM, rather than using RSA to encrypt entire requests and responses.

There are two primary problems here.

**First problem: The browser and the server must negotiate a session key.**

During subsequent transmission of HTTP requests, Cookies, and response bodies, this session key is used for symmetric encryption. Symmetric encryption is far better suited for processing large volumes of data; asymmetric encryption has high computational costs and is generally not used to directly encrypt entire web page contents.

**Second problem: The browser must confirm that the remote party is genuinely the intended website.**

If the server simply "sent a public key to the browser", a man-in-the-middle could easily send their own public key instead. The browser would mistakenly believe it was the target website's public key and encrypt secret data for the attacker. Certificates, CAs, and digital signatures exist to solve this exact problem: proving that this public key is authentically bound to this domain name, rather than injected by someone along the path.

Both the RSA handshake and the ECDHE handshake must address these two problems. They simply differ in how they solve "where the session key comes from".

## RSA Handshake: Key Material Sent Encrypted

### Full Handshake Flow

First, let's look at RSA key exchange in TLS 1.2.

The browser first sends `ClientHello`. This carries the TLS versions supported by the client, supported cipher suites, and a random number `Client Random`.

Upon receiving it, the server responds with `ServerHello`, selecting the TLS version and cipher suite, providing a random number `Server Random`, and sending its certificate to the client.

At this point, the client has obtained the server certificate. It verifies the certificate chain, domain name, validity period, and digital signature. Once certificate verification passes, the client extracts the server's RSA public key from the certificate.

Next comes the critical step: the client generates a new random value, known as the `PreMasterSecret`. In TLS 1.2 RSA key exchange, this value is **48 bytes**. The client encrypts the `PreMasterSecret` using the server's RSA public key taken from the certificate, places the encrypted result into `Client Key Exchange`, and sends it to the server.

The server receives it and decrypts it using its own RSA private key, obtaining the identical `PreMasterSecret`.

At this moment, both the client and the server hold three pieces of material:

```text
Client Random
Server Random
PreMasterSecret
```

Both parties then derive the `Master Secret` based on these three materials, from which subsequent session keys are derived. When actual HTTP requests and responses are transmitted, these derived symmetric keys are used.

To condense this into a single sentence:

**In an RSA handshake, the session key material is generated by the client, "packaged up", and sent to the server.**

Here, the "packaging" relies on the server's RSA public key. Only the server holding the corresponding RSA private key can unpack this package.

This sounds quite reasonable. The client generates the secret, the server decrypts it with its private key, both sides obtain the same material, and combine it with two random numbers to derive subsequent session keys.

However, the problem lies precisely here.

### Lack of Forward Secrecy: Long-Term Private Keys Are Too Valuable

Suppose an attacker captures a slice of HTTPS traffic today, but does not possess the server's private key at the time, and therefore cannot decipher the contents. The attacker can simply store this traffic.

A year later, if the server's RSA private key leaks, what happens?

In RSA key exchange, the `PreMasterSecret` originally sent by the client was encrypted using the server's RSA public key. If the attacker captured complete handshake plaintext random numbers (`Client Random`, `Server Random`) alongside the encrypted `PreMasterSecret`, they can combine these with the subsequently leaked server private key to decrypt that historical `PreMasterSecret`, and proceed to derive the exact session key used for that past connection.

Past data can now be fully decrypted.

Note the necessary conditions: it is not "as long as the private key leaks, all historical traffic can definitely be decrypted". The attacker must have captured sufficiently complete handshake and application data. If they only have unidirectional fragments or incomplete handshake logs, even with the private key, they may not be able to reconstruct that session.

However, from a security architecture perspective, this risk is unacceptable. Once a long-term private key acts as a master key capable of unlocking historical traffic, its compromise impacts not only future connections, but also retroactively invalidates the privacy of communications that occurred in the past.

The criticism here is not that the RSA algorithm itself is "unusable". RSA can still be used for signature authentication and remains common in certificate ecosystems. The flaw lies in "using an enduring, static server private key to decrypt key material from historical handshakes".

If the server private key leaks, the blast radius is catastrophic.

### Another Historical Burden: Padding Oracle Attacks

RSA key exchange carries another engineering complication: the `PreMasterSecret` is not encrypted raw, but formatted according to structures like RSAES-PKCS1-v1_5 before encryption.

This nuance historically paved the way for Bleichenbacher-style padding oracle attacks.

The general premise is: an attacker does not necessarily need to obtain the server private key immediately. Instead, they repeatedly construct various ciphertexts and send them to the server, observing differences in how the server handles padding errors, version errors, and length errors. If the server reveals behavioral differences in error codes, response times, logging, or connection termination methods, the attacker can gradually narrow down and recover the plaintext.

The troublesome part of this attack is that it is not purely a mathematical flaw, but an implementation vulnerability.

TLS 1.2 mandated defense requirements for this: even if decryption fails, the server must not expose the specific failure reason, but instead proceed through the rest of the flow using a randomly generated value to prevent attackers from inferring whether the ciphertext was close to a valid format based on diverging behavior.

Yet protocol specifications do not guarantee reliable implementations. The 2017 ROBOT attack demonstrated once again that some server implementations still exposed RSA decryption oracles due to subtle behavioral variances. A slight divergence in error codes, execution duration, logs, or branch paths can turn into a side channel.

Therefore, static RSA key exchange was phased out not only because it lacks forward secrecy, but also because it placed too heavy a burden on implementation subtleties.

### Can It Be Downgraded Back to RSA?

Here is another point that is easily misunderstood.

In TLS 1.2, the client supplies its supported cipher suites in `ClientHello`, and the server picks one supported by both. In theory, if the server continues to enable static RSA suites like `TLS_RSA_*`, legacy clients may continue to perform RSA handshakes.

However, this does not mean "a man-in-the-middle can simply strip ECDHE from ClientHello to quietly downgrade the connection to RSA". The handshake's concluding `Finished` message validates the handshake transcript; modifying `ClientHello` will generally cause verification to fail and terminate connection establishment.

Historically, downgrade attacks have occurred, such as FREAK and Logjam. They exploited the fact that certain clients and servers still supported export-grade weak cipher suites, combined with implementation and configuration vulnerabilities, forcing the connection down weaker RSA_EXPORT or DHE_EXPORT paths—not by "silently succeeding simply by deleting ECDHE". TLS 1.3 added downgrade protection values in `ServerHello.random`, reminding us that protocols continually patch historical attack surfaces.

What truly requires operational attention is the server configuration itself: if legacy client compatibility is no longer required, static RSA key exchange cipher suites should be disabled, retaining only suites that support forward secrecy. Otherwise, clients or misconfigurations in the environment may still fall back to RSA handshakes.

This is why, when auditing TLS configurations, you must inspect the actual negotiated cipher suite. Checking only that "the server supports ECDHE" is insufficient; you must verify whether it simultaneously retains legacy `TLS_RSA_*` suites.

## ECDHE Handshake: Key Material Negotiated by Both Parties

### The Core Idea of Diffie-Hellman

The `DHE` in ECDHE stands for Diffie-Hellman Ephemeral. The `EC` prefix stands for Elliptic Curve.

Don't be intimidated by the name. Setting elliptic curves aside for a moment, let's first examine what problem DH aims to solve.

The goal of DH is ingenious: both communicating parties never directly transmit the shared secret, yet both can independently compute the identical shared secret.

It can be roughly understood as follows:

The client generates a temporary private key (kept locally) and computes a temporary public key to send to the server. The server also generates a temporary private key (kept locally) and computes a temporary public key to send to the client.

Both parties only exchange public keys over the wire. An attacker eavesdropping on the network can see these public keys, but cannot see either party's temporary private key.

Next, the client uses its "own temporary private key + server's temporary public key" to compute the shared secret; the server uses its "own temporary private key + client's temporary public key" to compute the exact same shared secret.

The shared secret was never transmitted over the network.

ECDHE simply performs this process within an elliptic curve framework. While the mathematical theory of elliptic curves is more abstract, at equivalent security levels, it can achieve comparable cryptographic strength with significantly shorter keys, with computational and transmission overhead substantially lower than traditional finite-field DHE. To understand the TLS handshake, remembering one sentence is enough:

**In ECDHE, session key material is not generated by one party and shipped to the other; rather, both parties negotiate it via ephemeral keys.**

### Full Handshake Flow

Now let's examine the common `ECDHE_RSA` handshake in TLS 1.2.

The client still begins by sending `ClientHello`, containing TLS versions, supported cipher suites, and `Client Random`. The server responds with `ServerHello`, selecting a cipher suite, for example:

```text
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
```

This cipher suite name must be dissected carefully; don't assume that seeing RSA means it is still using RSA to encrypt the session key.

- `ECDHE` indicates the key exchange method.
- `RSA` indicates the authentication and signing method.
- `AES_256_GCM` indicates that subsequent record data uses AES with a 256-bit key length in GCM mode.
- `SHA384` specifies the hash algorithm used by the TLS 1.2 PRF and `Finished` message.

GCM itself already provides integrity protection at the record layer, so `SHA384` here no longer serves as a record-layer MAC, but primarily participates in key derivation and handshake transcript verification.

The server then sends its certificate. In `ECDHE_RSA`, the RSA public key in the certificate is primarily used to verify the server's signature, rather than having the client encrypt a `PreMasterSecret` with it.

Then, the ECDHE handshake diverges from the RSA handshake.

In an ECDHE handshake, the server sends `Server Key Exchange`. This message contains the elliptic curve parameters chosen by the server, along with the server's ephemeral ECDHE public key.

**Here comes the question: How does the client know this ephemeral ECDHE public key wasn't swapped by a man-in-the-middle?**

**The answer is the digital signature.**

The server signs these handshake parameters using the private key corresponding to its certificate. Upon receiving them, the client verifies the signature using the public key from the certificate. If the signature verification succeeds, the client confirms that this ephemeral ECDHE public key genuinely originated from the server holding the certificate private key, rather than being substituted en route.

Subsequently, the client generates its own ephemeral ECDHE private and public keys, sending its ephemeral public key to the server via `Client Key Exchange`.

At this step, both parties have the materials necessary to compute the shared secret.

The client holds:

```text
Client ephemeral private key
Server ephemeral public key
Client Random
Server Random
```

The server holds:

```text
Server ephemeral private key
Client ephemeral public key
Client Random
Server Random
```

Both sides independently calculate the identical shared secret, and derive the session keys used for subsequent communication.

Let's emphasize this once more:

**The RSA in ECDHE_RSA is not used to encrypt and transmit session keys. It is responsible for proving that "these ephemeral ECDHE parameters were truly issued by the server".**

This is the most common misunderstanding when people read cipher suite names.

### How to Read Cipher Suite Names

A TLS 1.2 cipher suite name can generally be parsed along this pattern:

```text
TLS_KeyExchangeAlgorithm_AuthenticationAlgorithm_WITH_SymmetricEncryptionAlgorithm_HashAlgorithm
```

For example:

```text
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
```

Can be broken down as:

```text
ECDHE: Key exchange
RSA: Identity authentication, i.e., server signature
AES_128_GCM: Subsequent record layer encryption algorithm
SHA256: Hash algorithm used by TLS 1.2 PRF and Finished message; if a GCM cipher suite, it no longer acts as record layer MAC
```

Now look at another one:

```text
TLS_RSA_WITH_AES_128_GCM_SHA256
```

Here, `RSA` appears before `WITH` without `ECDHE`, indicating that both key exchange and identity authentication are tied to RSA. This is a classic static RSA key exchange suite.

In TLS 1.3, cipher suite naming changed, for example:

```text
TLS_AES_128_GCM_SHA256
```

You will notice that it no longer encodes the key exchange and authentication methods into the cipher suite name. TLS 1.3 separated this information into other extensions and handshake messages; the cipher suite name primarily describes the record-layer AEAD algorithm and the hash algorithm used by HKDF.

Therefore, when you see TLS 1.3's `TLS_AES_128_GCM_SHA256`, do not mistake it for having "no key exchange". Key exchange is very much still present; it is simply no longer written in the TLS 1.2 naming convention.

## Forward Secrecy and Performance Trade-offs

### Why ECDHE Provides Forward Secrecy

The key is the `E`, standing for `Ephemeral`.

The private key in an ECDHE handshake is not the long-term private key from the server certificate, but a transient private key generated specifically for that handshake session. Once the connection terminates, that ephemeral material should no longer be retained.

Consequently: if an attacker records packets today and compromises the server certificate private key years later, they cannot retroactively reconstruct past ephemeral shared secrets using that long-term private key alone. This is because what participated in key negotiation during that handshake was the ephemeral ECDHE private key, not the certificate private key.

The certificate private key acts like a "signing pen", not a "safe key".

In RSA key exchange, the server private key directly opens the `PreMasterSecret` sent by the client; in ECDHE, the server private key merely signs ephemeral parameters to prove identity. It does not directly compute the per-connection shared secret.

This shift in role dictates the profound difference in how historical traffic is protected.

![ECDHE forward secrecy principle: long-term key vs ephemeral key](/media/jg/ext/oss.javaguide.cn/javaguide/cs-basics/network/https-rsa-ecdhe-ecdhe-forward-secrecy-principle--8c09c992.png)

However, forward secrecy is not a silver bullet.

If server-side random number generation is weak, if ephemeral private keys are logged, or if memory leaks occur in the implementation, ECDHE cannot save you. In engineering implementations, to reduce handshake overhead, some implementations might briefly reuse ephemeral DH/ECDH secret material: often referred to as "exponent reuse" in finite-field DH, and "ephemeral private key/scalar reuse" in ECDH. If reuse intervals are too long, the granularity of forward secrecy degrades.

Another risk stems from parameter validation. For instance, if the server fails to properly validate whether the elliptic curve point received from the client lies on a valid curve, it can leave room for invalid curve attacks. Typical developers might not write code at this layer, but it serves as a reminder: cryptographic security is not achieved merely by "picking the right algorithm"; TLS library implementation and configuration matter equally.

### The Impact of Session Resumption

Another easily overlooked consideration: **session resumption.**

A full ECDHE handshake requires ephemeral key negotiation, which carries notable overhead. To minimize handshake costs, TLS supports session resumption. When a client visits the same site subsequently, it can attempt to reuse previously negotiated session state, avoiding a full handshake every time.

The issue is that session resumption has its own security boundary.

Taking TLS 1.2 session tickets as an example, the server protects session state using a ticket encryption key (STEK). When the client later returns with the ticket, the server decrypts it to restore the session. If this ticket encryption key is not regularly rotated, once leaked, an attacker could decrypt historically captured tickets and reconstruct the key material for those resumed sessions.

In this scenario, the window of forward secrecy is no longer "a single connection", but is extended to "the lifetime of the ticket encryption key".

Thus, production configuration audits cannot simply stop at checking "whether ECDHE is enabled". How session ticket keys are generated, rotated, shared across multiple server nodes, and the blast radius of their potential compromise must also be factored in.

### Performance Is Not Free

While ECDHE provides forward secrecy, it also introduces costs.

The primary path of RSA key exchange involves the server decrypting the client's `PreMasterSecret` with its long-term RSA private key. In contrast, ECDHE_RSA requires completing ephemeral ECDH negotiation and signing the server's ephemeral parameters.

For high-concurrency services, TLS handshakes consume noticeable CPU cycles, particularly when short-lived connections dominate and session resumption hit rates are low.

We cannot simply claim that "ECDHE is always slower than RSA". Actual overhead depends on RSA key length, elliptic curve choice, signature algorithm, TLS library implementation, CPU instruction sets, and session resumption hit rates. For example, X25519, P-256, RSA 2048, and RSA 3072 exhibit differing benchmarks across various CPUs and TLS libraries.

To genuinely assess overhead, the most reliable method is running load tests on target production hardware rather than quoting third-party static figures. You should distinguish between three levels of measurement:

```text
1. Latency of single cryptographic operation
2. Latency of full TLS handshake
3. End-to-end latency of business requests
```

The first can be roughly evaluated using `openssl speed` to gauge orders of magnitude (e.g., testing RSA, ECDH, and X25519 computation throughput); the second reflects TLS library and server configurations; the third is further influenced by network round trips, connection reuse, and application logic.

Consequently, production systems rarely rely on "switching to ECDHE" alone. Standard practice pairs it with TLS 1.3, session resumption, rational certificate algorithms and curves, and hardware acceleration where necessary.

Security and performance are not mutually exclusive, but neither should we pretend security comes without performance cost.

## Changes in TLS 1.3

Looking strictly at TLS 1.2, RSA and ECDHE can be compared as two alternative key exchange mechanisms.

In TLS 1.3, however, static RSA key exchange has been eliminated, and the handshake structure has been overhauled.

A full TLS 1.2 handshake generally requires 2 RTTs. The client sends `ClientHello`, the server responds with `ServerHello`, certificates, and related handshake messages, the client follows with key exchange and `Finished`, and the server finally responds with `Finished`.

TLS 1.3 places key exchange parameters directly inside the `key_share` extension of `ClientHello`. The server can return its own `key_share` in its very first response, collapsing the full handshake down to 1 RTT.

How many milliseconds 2 RTTs to 1 RTT saves depends on network conditions. Within the same datacenter, it may only save a few milliseconds; across geographical regions, on mobile networks, or in high packet-loss environments, eliminating an RTT is much more noticeable.

However, TLS 1.3 does not guarantee 1 RTT in every circumstance. If the client's `key_share` does not match the curves supported by the server, the server responds with a `HelloRetryRequest`, instructing the client to resend with compatible parameters. In that scenario, the handshake approaches 2 RTTs again.

Therefore, in production environments, client and server support for common key exchange groups should be aligned (such as `X25519` and `secp256r1`). Otherwise, the 1-RTT advantage of TLS 1.3 can be compromised.

## RSA vs ECDHE Core Differences Quick Reference

Summarizing them side-by-side makes the distinction clear:

| Comparison Item | RSA Key Exchange | ECDHE Key Exchange |
| --- | --- | --- |
| Typical Version Context | Seen in TLS 1.2 and earlier | Common in TLS 1.2; continued as primary ephemeral negotiation in TLS 1.3 |
| How Session Key Material Originates | Client generates `PreMasterSecret`, encrypts with server RSA public key and sends | Both parties generate ephemeral key pairs and compute shared secret via ECDHE |
| Role of Server Private Key | Decrypts `PreMasterSecret` sent by client | Signs ephemeral ECDHE parameters to prove they originate from authentic server |
| What Is Transmitted on the Wire | Encrypted `PreMasterSecret` | Ephemeral public keys from both sides and signed parameters |
| Forward Secrecy Support | Not supported | Supported, provided ephemeral keys are securely generated and discarded after use |
| Impact of Private Key Leak | If handshake data was completely captured, historical traffic can potentially be decrypted | Compromising certificate private key alone generally cannot decrypt historical traffic |
| Typical Vulnerabilities / Issues | Long-term private key carries excessive value; historical PKCS#1 v1.5 padding oracle baggage | Handshake entails additional computational cost; parameter validation and ephemeral key hygiene depend on implementation |
| TLS 1.3 Status | Static RSA key exchange removed | Ephemeral key negotiation is the mainline standard |

### Common Misconception: ECDHE_RSA Does Not Mean Both Algorithms Encrypt

The name `ECDHE_RSA` easily leads people to assume both algorithms are encrypting data. Taking this cipher suite as an example:

```text
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
```

The division of labor is: ECDHE handles key exchange, RSA handles authentication signing, AES-256-GCM protects record-layer data, and SHA384 is used for TLS 1.2 PRF and `Finished` validation. RSA certificate signing and RSA key exchange are two distinct functions; the former remains common in modern HTTPS, whereas the latter has been removed from TLS 1.3.

## How to Answer in Interviews: RSA vs ECDHE in HTTPS Handshake, What Is the Real Difference?

The core distinction between RSA and ECDHE is whether session key material is "sent across the wire" or "negotiated independently".

In a TLS 1.2 static RSA handshake, the client generates the `PreMasterSecret`, encrypts it with the server's RSA public key from the certificate, and sends it to the server, which decrypts it with its RSA private key. The problem is that if an attacker captures and saves the handshake traffic and the server private key leaks in the future, the attacker can decrypt past session keys, meaning it lacks forward secrecy.

ECDHE does not transmit the shared secret directly. The client and server each generate ephemeral key pairs, exchange ephemeral public keys, and independently calculate the identical shared secret locally. The server's certificate private key is used solely for digital signatures to prove the ephemeral parameters were not altered by a man-in-the-middle, not to decrypt the session key.

In an interview, you can answer like this: In TLS 1.2 static RSA handshakes, the client generates the `PreMasterSecret` and sends it encrypted with the server's RSA public key; if an attacker captures the complete handshake traffic and obtains the server private key later, historical sessions can be decrypted, so it lacks forward secrecy. ECDHE does not transmit the shared secret directly; both sides exchange ephemeral public keys and derive the same secret locally. The certificate private key is used primarily for signature authentication rather than directly decrypting session keys. TLS 1.3 has completely removed static RSA key exchange, relying on (EC)DHE, PSK, or a combination of both for key establishment.
