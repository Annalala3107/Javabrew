## MyBatis Fundamentals

### What Is MyBatis? Why Is It Called a Semi-Automatic ORM?

MyBatis is a persistence-layer framework. It encapsulates repetitive JDBC boilerplate such as creating connections, binding parameters, executing SQL, iterating over result sets, and closing resources, while allowing developers to write SQL themselves and map both parameters and query results to Java objects.

MyBatis is often referred to as a semi-automatic ORM because SQL statements, column mappings, and association queries generally remain under the developer's control. Whereas ORM frameworks like Hibernate/JPA emphasize generating SQL from entity relationships and mapping metadata, MyBatis leaves control of SQL in the hands of the developer.

This design fits projects with complex SQL, strict performance tuning needs, or heavy reliance on database-specific features. The trade-off is more SQL and mapping code, and developers must also handle SQL dialect migration, association loading, and batch operations themselves.

### What Are the Differences Between MyBatis and JPA/Hibernate?

| Comparison Dimension | MyBatis                                                               | JPA/Hibernate                                                            |
| -------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| SQL                  | Typically written by the developer                                    | Typically generated by the framework from mappings                       |
| Control Granularity  | Easy to precisely control SQL, indexes, and database-specific features | Focuses more on the object model and persistence state                   |
| Development Cost     | More mapping and SQL code                                             | Less boilerplate code for standard CRUD                                  |
| Database Migration   | Hand-written SQL may depend on database dialects                      | Standard queries generally have better portability                       |
| Association Queries  | Explicitly choose JOINs or nested queries                             | Supports object associations and fetch strategies                        |
| Common Risks         | Scattered SQL, mapping errors, string-concatenation SQL injection     | N+1 queries, over-fetching, generated SQL that is hard to control        |

No single solution fits every project. When most operations are straightforward CRUD and the domain model is stable, JPA/Hibernate can cut down repetitive code; when reporting, complex queries, and SQL tuning dominate, MyBatis is more direct. Different modules within the same system can also choose whichever fits best.

### What Are the Core Components of MyBatis?

- **`SqlSessionFactoryBuilder`**: Reads configuration and builds a `SqlSessionFactory`. Once built, it can generally be discarded.
- **`SqlSessionFactory`**: Creates `SqlSession` instances. Building it is expensive, so typically a single instance is kept for the lifetime of the application.
- **`SqlSession`**: Executes SQL, manages transactions, and retrieves Mappers. It is not thread-safe and should be scoped to a single request, method, or transaction.
- **`Configuration`**: Holds global settings, `MappedStatement`, `ResultMap`, `TypeHandler`, plugins, and other runtime metadata.
- **`MappedStatement`**: Represents a single `<select>`, `<insert>`, `<update>`, or `<delete>` mapped statement.
- **`Executor`**: Responsible for queries, updates, the first-level cache, and transaction-related calls.
- **`StatementHandler`**: Creates and interacts with JDBC `Statement` objects.
- **`ParameterHandler`**: Sets parameters onto a `PreparedStatement`.
- **`ResultSetHandler`**: Maps a JDBC `ResultSet` into Java objects.

`SqlSource` holds the SQL generation logic; at execution time, it generates a `BoundSql` based on the input parameters, containing the final SQL, parameter mappings, and additional parameters.

### Are `SqlSessionFactory`, `SqlSession`, and Mapper Thread-Safe?

Once built, `SqlSessionFactory` can be shared across the application. `SqlSession` holds mutable state such as a database connection, transaction state, and first-level cache, so it must not be shared across threads. A Mapper proxy obtained from a specific `SqlSession` should follow the same lifecycle.

In MyBatis-Spring, injected Mappers are backed by `SqlSessionTemplate`. `SqlSessionTemplate` is thread-safe: it locates the `SqlSession` bound to the current Spring transaction and manages commit, rollback, and closing lifecycles. Therefore, a Spring singleton Service can safely inject a Mapper, but you must never store a manually created native `SqlSession` in a singleton field.

### ⭐️ How Does the Mapper Interface Work?

MyBatis creates a proxy object for a Mapper interface using JDK Dynamic Proxy. When a Mapper method is invoked, execution roughly follows this chain:

1. `MapperProxy` intercepts the interface method call.
2. MyBatis derives the Statement ID from the Mapper interface's fully qualified name and the method name, such as `com.example.UserMapper.selectById`.
3. `MapperMethod` inspects the parameters and return type, then delegates to the corresponding `SqlSession` method (`selectOne()`, `selectList()`, `insert()`, etc.).
4. `SqlSession` looks up the `MappedStatement` by Statement ID and hands it off to `Executor` for execution.
5. After `ResultSetHandler` maps the query result, it is returned according to the return type declared on the Mapper method.

A Mapper interface typically has no concrete implementation class. The interface's fully qualified name should match the XML `namespace`, and each method name should match the corresponding mapped statement's `id`.

### Can Methods in a Mapper Interface Be Overloaded?

Java allows declaring overloaded methods in a Mapper interface, but MyBatis looks up mapped statements using "fully qualified interface name + method name" without including parameter types in the Statement ID. Likewise, an XML file cannot define two mapped statements with the same `id` under the same `namespace`.

While multiple overloaded methods can share a single dynamic SQL statement in rare cases, MyBatis cannot dispatch to different SQL statements by parameter signature the way the Java compiler resolves overloads, and parameter names, return types, and dynamic conditions easily conflict. In real projects, use distinct method names to represent distinct queries.

### ⭐️ What Is the Complete Execution Flow of a Query in MyBatis?

You can answer this in two parts: startup-time parsing and runtime execution.

Startup time:

1. Read the global MyBatis configuration and create `Configuration`.
2. Parse Mapper XML files or annotations, registering SQL, parameter mappings, and result mappings as `MappedStatement`, `ResultMap`, and `SqlSource` objects.
3. Build `SqlSessionFactory`, and in Spring projects, register the Mapper proxies.

Runtime:

1. Invoke the Mapper proxy and locate the `MappedStatement` by interface name and method name.
2. `SqlSource` generates `BoundSql` from the actual arguments.
3. `Executor` checks the first-level cache according to caching rules; on a cache miss, it proceeds to query the database.
4. `StatementHandler` creates the JDBC `Statement`, and `ParameterHandler` binds the parameters.
5. JDBC executes the SQL, and `ResultSetHandler` maps the result set into Java objects.
6. Results are written to the cache if applicable and returned; when the transaction ends, it is committed or rolled back.

Plugins can wrap `Executor`, `StatementHandler`, `ParameterHandler`, and `ResultSetHandler`, so pagination, auditing, and SQL rewriting may intercept this chain.

## Parameter Handling and Dynamic SQL

### ⭐️ What Is the Difference Between `#{}` and `${}`?

In mapped SQL:

- `#{}` produces a JDBC parameter placeholder `?`, and MyBatis binds the value via `ParameterHandler` and `TypeHandler`. Because the parameter is sent to the database as data, it generally prevents SQL injection at that position.
- `${}` substitutes the expression result directly into the SQL text without creating a bind parameter. It can alter column names, table names, sort directions, or entire SQL fragments, which introduces SQL injection risk.

```xml
<select id="findByName" resultType="User">
  SELECT id, name
  FROM users
  WHERE name = #{name}
  ORDER BY ${orderBy}
</select>
```

`name` should use `#{}`. If `orderBy` comes directly from an external request, an attacker can alter the SQL; external values should be mapped in Java code to server-side predefined column names and sort directions.

`${}` also appears in MyBatis configuration files, such as `${driver}` or `${url}`. That syntax performs configuration property substitution during configuration parsing, which is a different mechanism from dynamic text substitution in mapped SQL.

### How Do You Reference Parameters When a Mapper Method Has Multiple Parameters?

It is recommended to explicitly name parameters with `@Param`:

```java
User selectByTenantAndId(
    @Param("tenantId") Long tenantId,
    @Param("userId") Long userId
);
```

```xml
<select id="selectByTenantAndId" resultType="User">
  SELECT id, name
  FROM users
  WHERE tenant_id = #{tenantId}
    AND id = #{userId}
</select>
```

Without `@Param`, MyBatis exposes generic names such as `param1` and `param2`. If the project is compiled with `-parameters` and `useActualParamName` is enabled, actual parameter names can also be read. However, changes in compiler flags can make actual parameter names unavailable, so using `@Param` on public Mappers is much more reliable.

Collection parameters can be referenced by names such as `collection`, `list`, or `array`, depending on the parameter type and `@Param`. Explicitly annotating a collection with `@Param("ids")` and referencing `<foreach collection="ids">` improves readability.

### ⭐️ What Dynamic SQL Tags Does MyBatis Provide, and How Do They Work?

Common tags include:

- `<if>`: Conditionally appends SQL fragments.
- `<choose>`, `<when>`, `<otherwise>`: Picks one branch out of multiple options.
- `<trim>`, `<where>`, `<set>`: Handles prefixes, suffixes, extra `AND`s, trailing commas, and similar formatting issues.
- `<foreach>`: Iterates over collections, commonly used for `IN` clauses and batch inserts.
- `<bind>`: Creates a variable usable within the current dynamic SQL block.

When parsing dynamic SQL, MyBatis turns XML nodes into a composite tree of `SqlNode` objects. When the Mapper method runs, each node evaluates OGNL expressions against the parameter context to decide whether to emit SQL, and `DynamicSqlSource` produces the final `BoundSql`.

```xml
<select id="find" resultType="User">
  SELECT id, name, status
  FROM users
  <where>
    <if test="name != null and name != ''">
      name = #{name}
    </if>
    <if test="status != null">
      AND status = #{status}
    </if>
  </where>
</select>
```

`<where>` outputs `WHERE` only when its inner content is non-empty, and strips any leading redundant `AND` or `OR`.

### What Are the Common Elements in Mapper XML?

- `<cache>`, `<cache-ref>`: Configures the second-level cache for the current namespace or references another namespace's cache.
- `<resultMap>`: Defines mappings between result sets and Java objects.
- `<sql>`, `<include>`: Defines and reuses SQL fragments.
- `<select>`, `<insert>`, `<update>`, `<delete>`: Defines mapped SQL statements.
- `<selectKey>`: Executes a key-retrieval query before or after an insert.

Older guides often mention `<parameterMap>`, but it has been deprecated; inline parameter mappings should be used instead.

A `<sql>` fragment can be defined after an `<include>` that references it. When MyBatis parses a Mapper XML file, it collects and registers `<sql>` fragments in the current file before parsing CRUD statements, so referenced fragments do not have to appear earlier in the file. For cross-resource references that cannot yet be resolved, MyBatis puts them into a pending collection and retries once the relevant definitions load. Even so, mapping files should follow the order recommended in the official documentation to avoid circular references and hard-to-maintain cross-file dependencies.

### What Internal Objects Is Mapper XML Parsed Into?

- Each `<select>`, `<insert>`, `<update>`, or `<delete>` is registered as a `MappedStatement`.
- Static SQL typically maps to `RawSqlSource`, while dynamic SQL typically maps to `DynamicSqlSource`.
- At runtime, `SqlSource` produces `BoundSql`, containing the final SQL and a list of `ParameterMapping` objects.
- `<resultMap>` is parsed into a `ResultMap`, and its child mappings become `ResultMapping` objects.
- `<cache>` creates and decorates a namespace-level cache instance.

These objects are stored inside `Configuration`. During normal runtime execution, this metadata should only be read rather than arbitrarily mutated globally.

## Result Mapping

### What Is the Difference Between `resultType` and `resultMap`?

`resultType` directly specifies the return object type and works well for simple queries where column names and property names align automatically. SQL column aliases can also assist matching, such as `user_name AS userName`.

`resultMap` explicitly describes the relationship between columns and properties, and also supports constructor mapping, type handlers, discriminators, and nested `<association>` and `<collection>` mappings, making it suited for complex objects and association queries.

```xml
<resultMap id="userMap" type="User">
  <id property="id" column="user_id" />
  <result property="userName" column="user_name" />
</resultMap>
```

Auto-mapping can work with `mapUnderscoreToCamelCase=true` to map `user_name` to `userName`. For complex JOIN queries, avoid relying solely on full auto-mapping; alias duplicate column names and configure them explicitly in `resultMap`.

### ⭐️ What Is the Difference Between `association` and `collection`?

- `<association>` maps a "has-one" relationship, such as an order belonging to one user.
- `<collection>` maps a "has-many" relationship, such as a user having multiple orders.

There are two common ways to load associations:

1. **Nested Results**: Fetches the parent and associated objects together via a JOIN, then deduplicates rows based on `<id>` and related mappings. This reduces the number of SQL queries, though the result set may expand significantly.
2. **Nested Select**: Queries the parent object first, then executes another mapped statement for the associated property. This structure is simple and supports lazy loading, but can easily cause N+1 queries.

When mapping one-to-many relationships via a JOIN, `<id>` should be properly configured on both the parent and child objects. MyBatis uses these identifiers to reuse existing objects and assemble collections; omitting them increases object-creation and mapping overhead and can even produce incorrect results.

### What Is an N+1 Query? How Can It Be Avoided?

Executing 1 query to fetch N parent records and then 1 query per record to fetch its associated objects results in 1 + N SQL queries—commonly known as an N+1 query. Both nested selects and lazy loading can trigger it.

Common ways to avoid it include:

- Fetching in a single query using a JOIN with nested result mapping.
- Batch-querying parent records first, then batch-querying associated records by the set of primary keys, and assembling them in memory.
- Coalescing requests in batch in scenarios like GraphQL/DataLoader.
- Using lazy loading only when a small number of associations will actually be accessed, and verifying query counts via SQL monitoring.

More JOINs are not always better either. With deep one-to-many hierarchies, Cartesian products can cause the result set to explode in size; splitting into two batch queries is often much easier to control.

### Does MyBatis Support Lazy Loading? How Does It Work?

MyBatis supports lazy loading for `<association>` and `<collection>` elements configured with nested selects. When `lazyLoadingEnabled` is enabled, MyBatis wraps pending properties using a proxy object; when those properties are accessed, the proxy executes the registered query and populates the result.

`fetchType="lazy"` or `fetchType="eager"` can override the global setting for an individual association. MyBatis 3.5.x uses Javassist by default to create lazy-loading proxies; CGLIB support was deprecated starting in 3.5.10.

Lazy loading has two common pitfalls: first, accessing collections in loops can trigger N+1 queries; second, accessing properties after the object has left its `SqlSession` or transaction scope may fail to load. When an API returns DTOs, it is usually cleaner to explicitly fetch all required data inside the Service layer.

### What Is the Role of `TypeHandler`, and How Are Enums Mapped?

`TypeHandler` converts between Java types and JDBC types: it translates Java values to JDBC values when setting `PreparedStatement` parameters, and converts JDBC values back to Java values when reading a `ResultSet`.

By default, MyBatis uses `EnumTypeHandler` to store enum names, such as `ACTIVE`. `EnumOrdinalTypeHandler` stores enum ordinals, but reordering enum constants later breaks existing data, so ordinals are generally discouraged for long-term database persistence.

Business enums usually have a stable `code` field; you can implement a custom `BaseTypeHandler` to map between `code` and the enum instance. When registering it, be explicit about `javaType`, any required `jdbcType`, and null-handling behavior.

### How Should You Troubleshoot Empty Query Results or Incomplete Mapping?

Check in the following order:

1. Verify whether the SQL actually returns rows and whether parameter values and JDBC types are correct.
2. Confirm that `namespace`, Statement ID, and the Mapper method match.
3. Check whether column aliases align with Java property names and whether camel-case auto-mapping is enabled as expected.
4. Verify `column`, `property`, `javaType`, and `typeHandler` definitions in `resultMap`.
5. Check whether JOINs produce duplicate column names that overwrite values, and whether `<id>` elements in nested results are complete.
6. Check whether fields lack setters, constructor parameters fail to match, or Lombok-generated methods behave differently from expectations.
7. Check whether the first-level cache returned an earlier query result from the same `SqlSession`.

When enabling MyBatis SQL logging, inspect the actual bound parameters alongside the SQL—parameterized SQL with `?` placeholders alone does not reveal the actual query conditions.

### What Happens If `selectOne()` Matches Multiple Rows?

If no row is found, `selectOne()` returns `null`; if exactly one row is found, it returns that object; if more than one row is found, it throws `TooManyResultsException`. It does not automatically pick the first row.

If business logic requires a unique result, enforce data consistency with a unique constraint. Only use sorting with `LIMIT 1` when business requirements explicitly permit "pick any one" or "pick the latest one"—never use it to mask dirty data.

## MyBatis Caching

### ⭐️ What Is the MyBatis First-Level Cache?

The first-level cache is a local cache scoped to `SqlSession`, with `SESSION` as its default scope. Within the same `SqlSession`, if two queries produce the same cache key from their Statement ID, final SQL, parameters, pagination bounds, and environment, the second query can return the cached result directly.

The first-level cache is also used to resolve circular references in nested result mappings. Setting `localCacheScope` to `STATEMENT` restricts local caching to the duration of a single statement execution, so it is no longer shared across two separate queries.

The following operations invalidate or clear the relevant first-level cache:

- Executing `insert`, `update`, or `delete`.
- Calling `clearCache()`.
- Committing, rolling back, or closing the `SqlSession`.
- Configuring `flushCache="true"` on a query statement.

### Why Does the First-Level Cache Seem Not to Work in a Spring Project?

The first-level cache lives inside the underlying `SqlSession`. In Spring, `SqlSessionTemplate` reuses the `SqlSession` bound to the current transaction; if there is no active transaction, each Mapper call closes the newly created session upon completion, so the next call may receive a brand-new `SqlSession`.

Therefore, if a single Service method calls a Mapper twice without entering a Spring transaction, you cannot assume the two calls share a first-level cache. At the same time, you should not artificially widen transaction boundaries just to "hit the cache"—transaction boundaries should still be determined by business consistency requirements.

### ⭐️ What Is the MyBatis Second-Level Cache, and How Do You Enable It?

The second-level cache is bound to a Mapper XML's `namespace` and can be shared across different `SqlSession` instances. Globally, `cacheEnabled` is enabled by default, yet each specific namespace still requires `<cache/>` or `<cache-ref>` referencing another namespace's cache.

```xml
<mapper namespace="com.example.UserMapper">
  <cache />

  <select id="selectById" resultType="User" useCache="true">
    SELECT id, name FROM users WHERE id = #{id}
  </select>
</mapper>
```

Query results typically become visible in the second-level cache to other sessions only after the transaction commits. Executing an insert, update, or delete in that namespace clears the cache by default. `useCache` and `flushCache` can customize behavior at the individual statement level.

The default cache configuration may require result objects to be serializable; if you swap in a third-party cache or adjust `readOnly`, object copying and thread-safety semantics also change and should be verified against the specific implementation.

### Why Should Production Projects Be Cautious with the MyBatis Second-Level Cache?

- Caching is organized by `namespace`; when another Mapper modifies the same table, caches in other namespaces are not automatically notified.
- Data may be modified by other applications, scripts, or direct SQL, which MyBatis cannot detect automatically.
- The local second-level cache resides only within the current application instance and does not synchronize across multiple instances.
- JOIN queries depend on multiple tables, so a change in any involved table can make cached results stale.
- Large cached objects or low hit rates consume memory with little benefit.

When cross-instance sharing and explicit invalidation strategies are needed, teams usually implement caching at the service/application layer with Redis or Caffeine while treating the database as the source of truth. MyBatis second-level caching is better suited to read-heavy, rarely changing data with clean table dependencies.

### Can the First-Level Cache Cause Dirty Reads?

After a `SqlSession` runs a query once, if the database is updated by another transaction or application, running the same query again in that `SqlSession` may still return the stale object from its first-level cache. While this is not a dirty read in the strict database isolation-level sense, it manifests to the application as stale data.

When fresh external data is required, you can call `clearCache()`, shorten the session lifecycle, set `localCacheScope` to `STATEMENT`, or run the query in a new transaction/session. Do not expect that merely clearing the cache inside an ongoing transaction guarantees visibility of other transactions' updates—the final visibility is still governed by the database isolation level.

## Executor, Batch Processing, and Plugins

### What Executors Does MyBatis Provide?

| ExecutorType | Behavior                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| `SIMPLE`     | Creates a new `PreparedStatement` for every execution; this is the default type                        |
| `REUSE`      | Reuses the `PreparedStatement` matching the SQL within the current `SqlSession`                        |
| `BATCH`      | Reuses statements for updates and invokes JDBC Batch; flushes batches before queries or upon commit    |

All three `Executor` types are scoped to `SqlSession`. `REUSE` reuses the `Statement` object, not query results; query result reuse is handled by caching.

You can select the executor via global `defaultExecutorType`, `openSession(ExecutorType)`, or `SqlSessionTemplate` constructor arguments. Do not switch `ExecutorType` within the same Spring transaction; if another type is genuinely required, run it in an independent transaction or outside the transaction.

### ⭐️ How Does MyBatis Execute Batch Processing?

You can use `ExecutorType.BATCH`, repeatedly call Mapper `insert`, `update`, or `delete` methods, and then invoke `flushStatements()` or commit the transaction. `BatchExecutor` groups operations by `Statement` and SQL, then invokes JDBC `addBatch()` and `executeBatch()`.

Key caveats for batch processing:

- Do not accumulate unbounded amounts of data at once; call `flushStatements()` and clear the session cache at fixed batch intervals.
- Executing a query midway flushes any queued batches.
- The return value of an individual Mapper call is not necessarily the final affected row count; batch results are obtained after flushing.
- If `BatchUpdateException` occurs, some preceding statements may already have been executed by the database; evaluate together with transaction rollback and driver return results.
- Multi-row insert SQL, JDBC Batch, and database-native Bulk Load are different mechanisms with distinct performance profiles and generated-key support.

In MyBatis-Spring, do not manually commit or close `SqlSessionTemplate`; let Spring transaction management handle commit and rollback.

### Can Batch Inserts Populate Auto-Generated Primary Keys?

Provided the database and JDBC driver support it, auto-increment primary keys can be populated back via `useGeneratedKeys="true"` and `keyProperty`. When the parameter is a list of objects, the driver must properly return generated keys for every row so MyBatis can write them back in order.

```xml
<insert id="batchInsert"
        useGeneratedKeys="true"
        keyProperty="id">
  INSERT INTO users (name, status)
  VALUES
  <foreach collection="list" item="item" separator=",">
    (#{item.name}, #{item.status})
  </foreach>
</insert>
```

Support varies significantly across databases, driver versions, and batch SQL syntax, so verify key counts and ordering with integration tests. When JDBC generated keys cannot be relied upon, generate UUIDs or Snowflake IDs on the application side, or use `<selectKey>` according to database capabilities.

### What Is the Difference Between `useGeneratedKeys` and `<selectKey>`?

- `useGeneratedKeys` relies on JDBC `getGeneratedKeys()` and is commonly used for database auto-increment primary keys.
- `<selectKey>` executes an additional query and can be configured to run before or after the insert, making it suitable for sequences, database-specific functions, or legacy databases.

`keyProperty` specifies which Java property receives the key, and `keyColumn` specifies the database column when needed. Batch inserts, composite keys, and multi-datasource setups should be verified independently—never assume batch behavior matches single-row insert success.

### ⭐️ How Does Pagination Work in MyBatis? How Do Pagination Plugins Work?

MyBatis provides `RowBounds`, but it does not automatically append `LIMIT` to SQL. By default, it still executes the original SQL and skips `offset` rows while limiting the returned count in result-set handling. With large datasets or deep offsets, this approach can read huge volumes of discarded rows.

Production queries typically take one of two approaches:

- Explicitly write database-specific physical pagination in SQL.
- Use a pagination plugin such as PageHelper to rewrite the SQL by database dialect before execution and generate a `COUNT` query when needed.

Pagination plugins intercept objects such as `Executor` or `StatementHandler` through the MyBatis plugin mechanism, inspect `MappedStatement`, `BoundSql`, and pagination parameters, and build the rewritten paginated SQL. Plugins still have to handle SQL dialects, parameter ordering, `COUNT` SQL generation, thread-local context cleanup, and multi-datasource routing.

Even with `LIMIT offset, size`, deep pagination may still scan and discard large numbers of rows. Cursor-based pagination using a stable sort key—such as `WHERE id > ? ORDER BY id LIMIT ?`—can address this.

### How Do MyBatis Plugins Work, and How Do You Write One?

MyBatis plugins can intercept specific methods on four component interfaces:

- `Executor`
- `StatementHandler`
- `ParameterHandler`
- `ResultSetHandler`

A plugin implements `Interceptor` and uses `@Intercepts` and `@Signature` to declare target interfaces, methods, and parameter types. When MyBatis constructs those components, it calls `pluginAll()`, wrapping matching targets in JDK dynamic proxies; calling a targeted method dispatches into `intercept()`.

```java
@Intercepts({
    @Signature(
        type = Executor.class,
        method = "update",
        args = {MappedStatement.class, Object.class}
    )
})
public class AuditInterceptor implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        // Perform only necessary processing and ensure the original method is ultimately invoked
        return invocation.proceed();
    }
}
```

Plugins sit on the main execution path of all matching SQL statements, so keep them lightweight and avoid mutating shared `MappedStatement` instances. Execution order across multiple plugins depends on configuration order and proxy nesting; when pagination, auditing, and data-permission plugins rewrite SQL together, test them in combination.

## Transactions, Performance, and Engineering Issues

### How Do Transactions Work in MyBatis-Spring?

MyBatis-Spring uses `SqlSessionTemplate` to bind a `SqlSession` to the active Spring transaction. Mapper calls within the same transaction and against the same `SqlSessionFactory` share the same session and database connection; the transaction commits when the method finishes normally and rolls back when an exception matching rollback rules is thrown.

Common pitfalls to watch out for:

- `@Transactional` must be invoked through the Spring proxy; self-invocation can bypass transaction interception.
- The transaction manager and `SqlSessionFactory` must share the same `DataSource`.
- Do not manually invoke `commit()`, `rollback()`, or `close()` on a Spring-managed `SqlSession`.
- Asynchronous threads do not automatically inherit the caller thread's transaction.
- Catching and swallowing an exception without rethrowing can cause Spring to treat the method as completed normally.

### Why Did a Mapper Call Succeed Without Data Being Committed?

Common causes include:

- Using `openSession()` manually defaults to non-auto-commit, and `commit()` was never called.
- The Spring transaction ultimately rolled back, or the transactional method threw a runtime exception.
- `@Transactional` did not take effect due to self-invocation, a non-Spring-managed object, or method visibility.
- Writes and subsequent reads used different data sources, and replica replication had not yet caught up.
- `BatchExecutor` was used without flushing batches or committing the transaction.

When troubleshooting, inspect transaction logs, data sources, connection `auto-commit` state, and any final exceptions together—do not rely solely on whether the Mapper method threw an error.

### How Do You Process Large Result Sets with MyBatis?

Returning an entire `List` loads all rows and mapped objects into memory at once. For large datasets, consider:

- Iterating row by row with `Cursor<T>`.
- Processing each row via a `ResultHandler` callback.
- Querying in batches using a stable sort key.
- Streaming reads and writes during data export while bounding buffer sizes.

`Cursor` depends on an open `SqlSession`, connection, and result set, so consumption must stay within their lifecycle. `fetchSize` is only a hint to the JDBC driver, and certain databases require specific cursor or connection flags. Streaming queries hold connections open longer, so configure timeouts, apply rate limiting, and avoid triggering N+1 queries inside the loop.

### How Do You Troubleshoot MyBatis SQL Performance Issues?

1. Capture the final SQL and actual bound parameters to confirm dynamic conditions match expectations.
2. Inspect the database execution plan, rows scanned, rows returned, sorting, and temporary tables.
3. Check indexes, implicit type conversions, functions on indexed columns, wildcard matching, and deep pagination.
4. Check for N+1 queries, selecting too many unnecessary columns, or batch operations degrading into single-row loops.
5. Separate time spent waiting on the connection pool, database execution, result-set transfer, and Java object mapping.
6. Check whether plugins, `TypeHandler`s, logging, or caching add extra overhead.

MyBatis is only one piece of the SQL execution chain. A "slow Mapper method" is not always caused by slow SQL itself—it can also stem from connection pool exhaustion, oversized result sets, or heavy CPU usage during object mapping.

### How Do You Prevent SQL Injection in MyBatis?

- Use `#{}` for value parameters by default; never concatenate user input into SQL.
- Map table names, column names, and sort directions via server-side enums to fixed SQL fragments.
- Use dynamic SQL only to toggle trusted SQL fragments, never to execute user-supplied expressions.
- Follow the principle of least privilege for database accounts to limit blast radius if injection occurs.
- Apply the same security review to string concatenation inside plugins and SQL Providers.

Parameterized queries protect only parameter value positions. `ORDER BY ${sort}`, `${tableName}`, and concatenated SQL returned by annotation Providers still require allowlisting.

### Can `id`s Be Duplicated Across Different Mapper XML Files?

Yes, provided their `namespace` values differ. The full ID of a `MappedStatement` is `namespace + id`, for example:

```text
com.example.UserMapper.selectById
com.example.OrderMapper.selectById
```

Two identical full IDs cannot be registered within the same `namespace`. When a Mapper XML file is paired with a Mapper interface, `namespace` is normally set to the fully qualified name of the Mapper interface.

### What Are Other Common Pitfalls When Using MyBatis?

- Assuming MyBatis completely eliminates SQL injection while overlooking `${}`, SQL Providers, and string concatenation in plugins.
- Treating Mapper method overloading as capable of mapping multiple SQL statements under the same name.
- Assuming `RowBounds` always performs database-level physical pagination.
- Treating the second-level cache as a cross-application consistent business cache.
- Storing a native `SqlSession` inside a singleton object.
- Persisting enum ordinals to the database and reordering enum constants in later versions.
- Accessing lazy-loaded properties inside loops, causing N+1 queries.
- Checking only the number of batch method calls without verifying whether the JDBC driver actually executes in Batch mode.
- Using `LIMIT 1` to hide duplicate-data bugs that should be prevented by unique constraints.
