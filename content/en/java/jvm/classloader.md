## Review of the Class Loading Process

Before introducing ClassLoaders and the Parent Delegation Model, let's briefly review the class loading process.

- Class loading process: **Loading -> Linking -> Initialization**.
- The Linking process can be further divided into three steps: **Verification -> Preparation -> Resolution**.

![Class loading process](/media/jg/ext/oss.javaguide.cn/javaguide/java/jvm/class-loading-procedure-a4b72893.png)

Loading is the first step of the class loading process and mainly accomplishes the following 3 tasks:

1. Obtain the binary byte stream that defines this class via its fully qualified class name.
2. Convert the static storage structure represented by the byte stream into a runtime data structure in the Method Area.
3. Generate a `Class` object representing this class in memory as the access entry point to these data in the Method Area.

## ClassLoader

### Introduction to ClassLoaders

ClassLoaders have existed since JDK 1.0, originally created to meet the needs of Java Applets (now deprecated/obsolete). Later, they gradually became an essential part of Java programs, giving Java the capability to dynamically load classes into the JVM and execute them.

According to the official API documentation:

> A class loader is an object that is responsible for loading classes. The class ClassLoader is an abstract class. Given the binary name of a class, a class loader should attempt to locate or generate data that constitutes a definition for the class. A typical strategy is to transform the name into a file name and then read a "class file" of that name from a file system.
>
> Every Class object contains a reference to the ClassLoader that defined it.
>
> Class objects for array classes are not created by class loaders, but are created automatically as required by the Java runtime. The class loader for an array class, as returned by Class.getClassLoader() is the same as the class loader for its element type; if the element type is a primitive type, then the array class has no class loader.

In essence, this means:

> A ClassLoader is an object responsible for loading classes. `ClassLoader` is an abstract class. Given the binary name of a class, the ClassLoader should attempt to locate or generate the data that constitutes the class definition. A typical strategy is to convert the name into a file name and then read the "class file" with that name from the file system.
>
> Every non-array class or interface has a reference pointing to the `ClassLoader` that defined it. Array classes are not created by a `ClassLoader`, but are created automatically by the JVM when needed; the ClassLoader of a reference-type array matches that of its element type, whereas a primitive-type array has no ClassLoader, and `getClassLoader()` returns `null`.

From the description above, we can see that:

- A ClassLoader is an object responsible for loading classes, implementing the Loading step in the class loading process.
- Every non-array class or interface records the `ClassLoader` that defined it.
- Array classes are not created by a `ClassLoader` (array classes have no corresponding binary byte stream), but are generated directly by the JVM; reference-type arrays inherit the defining ClassLoader of their element type, while primitive-type arrays have no ClassLoader.

```java
class Class<T> {
  ...
  private final ClassLoader classLoader;
  @CallerSensitive
  public ClassLoader getClassLoader() {
     //...
  }
  ...
}
```

Simply put, **the primary role of a ClassLoader is to dynamically load Java class bytecode (`.class` files) into the JVM (generating a `Class` object in memory representing the class).** The bytecode can be compiled from Java source files (`.java` files) via `javac`, dynamically generated by tools, or downloaded over a network.

In fact, in addition to loading classes, a ClassLoader can also load resources required by Java applications, such as text, images, configuration files, videos, and other file resources. This article focuses solely on its core function: loading classes.

### ClassLoader Loading Rules

When the JVM starts, it does not load all classes at once; instead, it loads them dynamically on demand. That is, most classes are only loaded when they are actually used, which is much more memory-friendly.

During class loading, `ClassLoader#loadClass` first uses `findLoadedClass` to check whether the JVM has already recorded the current ClassLoader as the initiating loader for the class with that binary name. If found, it returns the class directly; otherwise, it continues delegating or searching. A single ClassLoader cannot define two classes with the same binary name.

```java
// The following fields and methods are from the JDK 8 ClassLoader implementation and are shown only to illustrate how that version records classes
public abstract class ClassLoader {
  ...
  private final ClassLoader parent;
  // The classes loaded by this class loader.
  private final Vector<Class<?>> classes = new Vector<>();
  // Invoked by the VM to record every loaded class with this loader.
  void addClass(Class<?> c) {
        classes.addElement(c);
   }
  ...
}
```

### Summary of ClassLoaders

The three common built-in/standard ClassLoaders in JDK 8 are as follows:

1. **`BootstrapClassLoader` (Bootstrap ClassLoader)**: The top-level built-in ClassLoader of the JVM, typically represented as `null` in the Java API, with no parent ClassLoader. In JDK 8 HotSpot, it mainly loads core runtime libraries (such as `rt.jar`) and classes on paths specified by `-Xbootclasspath`.
2. **`ExtensionClassLoader` (Extension ClassLoader)**: Mainly responsible for loading JAR packages and classes under `%JRE_HOME%/lib/ext`, as well as all classes in paths specified by the `java.ext.dirs` system property.
3. **`AppClassLoader` (Application ClassLoader)**: The ClassLoader directly exposed to users, responsible for loading all JAR packages and classes on the current application's classpath.

> 🌈 Further Reading:
>
> - **`rt.jar`**: `rt` stands for "RunTime". `rt.jar` is the Java core class library, containing the class files for all classes seen in the Javadoc. In other words, the standard built-in packages `java.xxx.*` we commonly use—such as `java.util.*`, `java.io.*`, `java.nio.*`, `java.lang.*`, `java.sql.*`, and `java.math.*`—are all inside it.
> - After Java 9 introduced the module system, `rt.jar` and the extension directory mechanism were removed, and the Extension ClassLoader was replaced by the Platform ClassLoader. The Bootstrap, Platform, and Application ClassLoaders each define different runtime modules; it cannot simply be generalized that all modules other than `java.base` are loaded by the Platform ClassLoader.

In addition to these three ClassLoaders, users can add custom ClassLoaders for extension to satisfy special requirements. For example, we can encrypt Java bytecode (`.class` files) and decrypt it using a custom ClassLoader at load time.

![ClassLoader hierarchy diagram](/media/jg/ext/oss.javaguide.cn/javaguide/java/jvm/class-loader-parents-delegation-model-48efa806.png)

The Bootstrap ClassLoader is built into the JVM and is usually represented as `null` in the Java API. The Platform ClassLoader, Application ClassLoader, and typical custom ClassLoaders are all instances of `ClassLoader`. This allows users to customize ClassLoaders so applications can control how required classes are obtained.

Every `ClassLoader` can obtain its parent `ClassLoader` via `getParent()`. If the returned `ClassLoader` is `null`, then the parent ClassLoader of that ClassLoader is `BootstrapClassLoader`.

```java
public abstract class ClassLoader {
  ...
  // Parent ClassLoader
  private final ClassLoader parent;
  @CallerSensitive
  public final ClassLoader getParent() {
     //...
  }
  ...
}
```

**Why does calling `getClassLoader()` on a class defined by the Bootstrap ClassLoader return `null`?** Because the Bootstrap ClassLoader is a JVM built-in ClassLoader, and the Java API convention typically uses `null` to represent it; the specific language used to implement it is not part of the Java specification.

Let's look at a small example of retrieving `ClassLoader`s:

```java
public class PrintClassLoaderTree {

    public static void main(String[] args) {

        ClassLoader classLoader = PrintClassLoaderTree.class.getClassLoader();

        StringBuilder split = new StringBuilder("|--");
        boolean needContinue = true;
        while (needContinue){
            System.out.println(split.toString() + classLoader);
            if(classLoader == null){
                needContinue = false;
            }else{
                classLoader = classLoader.getParent();
                split.insert(0, "\t");
            }
        }
    }

}
```

Output (JDK 8):

```plain
|--sun.misc.Launcher$AppClassLoader@18b4aac2
    |--sun.misc.Launcher$ExtClassLoader@53bd815b
        |--null
```

From the output, we can see:

- The `ClassLoader` of our custom Java class `PrintClassLoaderTree` is `AppClassLoader`.
- The parent `ClassLoader` of `AppClassLoader` is `ExtClassLoader`.
- The parent `ClassLoader` of `ExtClassLoader` is `Bootstrap ClassLoader`, so the printed output is `null`.

### Custom ClassLoader

As mentioned earlier, except for `BootstrapClassLoader`, all other ClassLoaders are implemented in Java and inherit from `java.lang.ClassLoader`. If we want to define our own ClassLoader, we clearly need to inherit from the abstract class `ClassLoader`.

The `ClassLoader` class has two key methods:

- `protected Class loadClass(String name, boolean resolve)`: Loads the class with the specified binary name and implements the parent delegation mechanism. `name` is the binary name of the class; if `resolve` is `true`, `resolveClass(Class<?> c)` is invoked to link/resolve the class during loading.
- `protected Class findClass(String name)`: Finds the class by its binary name; the default implementation directly throws `ClassNotFoundException`.

The official API documentation states:

> Subclasses of `ClassLoader` are encouraged to override `findClass(String name)`, rather than this method.
>
> That is, subclasses of `ClassLoader` are recommended to override the `findClass(String name)` method rather than the `loadClass(String name, boolean resolve)` method.

If we do not want to break the Parent Delegation Model, we only need to override the `findClass()` method in `ClassLoader`—classes that cannot be loaded by parent ClassLoaders will ultimately be loaded through this method. However, if we want to break the Parent Delegation Model, we need to override the `loadClass()` method.

## Parent Delegation Model

### Introduction to the Parent Delegation Model

There are many types of ClassLoaders, so when we want to load a class, which ClassLoader actually loads it? This brings us to the Parent Delegation Model.

According to the official documentation:

> The ClassLoader class uses a delegation model to search for classes and resources. Each instance of ClassLoader has an associated parent class loader. When requested to find a class or resource, a ClassLoader instance will delegate the search for the class or resource to its parent class loader before attempting to find the class or resource itself. The virtual machine's built-in class loader, called the "bootstrap class loader", does not itself have a parent but may serve as the parent of a ClassLoader instance.

In essence, this means:

> The `ClassLoader` class uses a delegation model to search for classes and resources. Each `ClassLoader` instance has an associated parent ClassLoader. When asked to find a class or resource, a `ClassLoader` instance delegates the task of searching for the class or resource to its parent ClassLoader before attempting to find it itself.
> The virtual machine's built-in ClassLoader, known as the "bootstrap class loader", does not have a parent ClassLoader itself, but it can serve as the parent ClassLoader of a `ClassLoader` instance.

From the description above, we can see that:

- The `ClassLoader` class uses a delegation model to search for classes and resources.
- The Parent Delegation Model requires that, except for the top-level Bootstrap ClassLoader, all other ClassLoaders must have their own parent ClassLoader.
- A `ClassLoader` instance delegates the search for a class or resource to its parent ClassLoader before attempting to locate the class or resource itself.

The hierarchical relationship among the various ClassLoaders shown in the diagram below is called the **Parents Delegation Model** (or **Parent Delegation Model**) of ClassLoaders.

![ClassLoader hierarchy diagram](/media/jg/ext/oss.javaguide.cn/javaguide/java/jvm/class-loader-parents-delegation-model-48efa806.png)

Note ⚠️: The Parent Delegation Model is not a mandatory constraint; it is simply an approach recommended by the JDK. If we want to break the Parent Delegation Model due to certain special requirements, that is also possible—the specific methods will be introduced later.

Actually, the common Chinese name for this model literally translates as "two-parent delegation model," which can easily mislead people because "two parents" usually means both mother and father. Here, it simply refers to the parent tier/generation rather than implying there is literally a `MotherClassLoader` and a `FatherClassLoader`. Personally, "single-parent delegation model" would be a clearer translation, though since the conventional name has stuck in Chinese technical literature, using it is fine as long as there is no misunderstanding.

In addition, the parent-child relationship between ClassLoaders is generally not implemented through inheritance, but instead usually uses composition to reuse the parent ClassLoader's code.

```java
public abstract class ClassLoader {
  ...
  // Composition
  private final ClassLoader parent;
  protected ClassLoader(ClassLoader parent) {
       this(checkCreateClassLoader(), parent);
  }
  ...
}
```

In Object-Oriented Programming, there is a classic design principle: **Favor composition over inheritance; use more composition and less inheritance.**

### Execution Flow of the Parent Delegation Model

The core logic of the Parent Delegation Model is concentrated in `loadClass()` of `java.lang.ClassLoader`. Below is the relevant implementation snippet from JDK 8:

```java
protected Class<?> loadClass(String name, boolean resolve)
    throws ClassNotFoundException
{
    synchronized (getClassLoadingLock(name)) {
        // First, check whether the class has already been loaded
        Class c = findLoadedClass(name);
        if (c == null) {
            // If c is null, the class has not been loaded yet
            long t0 = System.nanoTime();
            try {
                if (parent != null) {
                    // When the parent ClassLoader is not null, delegate to parent.loadClass to load the class
                    c = parent.loadClass(name, false);
                } else {
                    // When the parent ClassLoader is null, invoke the Bootstrap ClassLoader to load the class
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // Thrown if the non-null parent ClassLoader cannot find the requested class
            }

            if (c == null) {
                // When the parent ClassLoader cannot load the class, invoke findClass to load it
                // Users can override this method to implement a custom ClassLoader
                long t1 = System.nanoTime();
                c = findClass(name);

                // Used to collect ClassLoader-related statistics
                sun.misc.PerfCounter.getParentDelegationTime().addTime(t1 - t0);
                sun.misc.PerfCounter.getFindClassTime().addElapsedTimeFrom(t1);
                sun.misc.PerfCounter.getFindClasses().increment();
            }
        }
        if (resolve) {
            // Link/resolve the class
            resolveClass(c);
        }
        return c;
    }
}
```

Whenever a ClassLoader receives a loading request, it first forwards the request to its parent ClassLoader. Only when the parent ClassLoader fails to find the requested class does the ClassLoader attempt to load it itself.

Combining the source code above, the execution flow of the Parent Delegation Model can be summarized as follows:

- During class loading, the system first checks whether the current class has already been loaded. A class that has already been loaded is returned directly; otherwise, loading is attempted (each parent ClassLoader goes through this same process).
- When a ClassLoader performs class loading, it does not try to load the class itself at first; instead, it delegates the request to its parent ClassLoader (by calling the parent's `loadClass()` method). Thus, all requests eventually reach the top-level `BootstrapClassLoader`.
- Only when the parent ClassLoader indicates that it cannot fulfill the loading request (the required class was not found in its search scope) will the child ClassLoader attempt to load the class itself (by calling its own `findClass()` method).
- If the child ClassLoader also fails to load the class, it throws a `ClassNotFoundException`.

🌈 Further Reading:

**Specific rules for how the JVM determines whether two Java classes are identical**: The JVM checks not only whether the two classes have the same fully qualified name, but also whether the ClassLoaders that loaded them are the same. Only when both are identical are the two classes considered the same. Even if two classes originate from the exact same `.class` file and are loaded by the same virtual machine, as long as their ClassLoaders differ, those two classes are definitely not identical.

### Benefits of the Parent Delegation Model

The Parent Delegation Model is an important part of Java's class loading mechanism. Parent-first delegation helps code within the same delegation chain reuse types already defined by parent ClassLoaders and reduces the risk of application code spoofing platform APIs; however, it does not prevent mutually independent ClassLoaders from separately defining classes with the same name.

The JVM distinguishes runtime types based on both the binary name of a class or interface and the ClassLoader that defined it. Parent delegation allows platform classes to be defined first by the appropriate built-in ClassLoaders, though not all core or platform APIs are loaded by the Bootstrap ClassLoader: starting with JDK 9, the Platform ClassLoader is also responsible for defining platform classes.

For example, the JVM prioritizes delegating requests for core classes like `java.lang.Object` to `BootstrapClassLoader`; moreover, `ClassLoader#preDefineClass` validates the class name during the definition phase and rejects any class name starting with `java.`, so core classes cannot be forged through a custom ClassLoader.

Many developers might ask: "Can't I just bypass the Parent Delegation Model?"

However, even if an attacker bypasses the Parent Delegation Model, Java still has lower-level security mechanisms to protect core libraries. The `preDefineClass` method in `ClassLoader` validates the class name before defining a class. Any class name starting with `"java."` triggers a `SecurityException`, preventing malicious code from defining or loading forged core classes.

The source code of `ClassLoader#preDefineClass` in JDK 8 is as follows:

```java
private ProtectionDomain preDefineClass(String name,
                                            ProtectionDomain pd)
    {
        // Check whether the class name is legal
        if (!checkName(name)) {
            throw new NoClassDefFoundError("IllegalName: " + name);
        }

        // Prevent defining classes in the "java.*" package.
        // This check is critical for security because it prevents malicious code from replacing core Java classes.
        // JDK 9 enhances the security of preDefineClass using the Platform ClassLoader
        if ((name != null) && name.startsWith("java.")) {
            throw new SecurityException
                ("Prohibited package name: " +
                 name.substring(0, name.lastIndexOf('.')));
        }

         // If no ProtectionDomain is specified, use the default domain (defaultDomain).
        if (pd == null) {
            pd = defaultDomain;
        }

        if (name != null) {
            checkCerts(name, pd.getCodeSource());
        }

        return pd;
    }
```

JDK 9 introduced the Platform ClassLoader, which can be obtained via `ClassLoader.getPlatformClassLoader()`. The `defineClass` restriction on `java.*` package names still exists, although the underlying implementation differs from JDK 8.

### How to Break the Parent Delegation Model

~~To avoid the parent delegation mechanism, we can define our own ClassLoader and simply override `loadClass()`.~~

**🐛 Correction (see: [issue871](https://github.com/Snailclimb/JavaGuide/issues/871))**: To create a custom ClassLoader, you need to inherit from `ClassLoader`. If we do not want to break the Parent Delegation Model, we simply override the `findClass()` method in `ClassLoader`, and classes that cannot be loaded by parent ClassLoaders will ultimately be loaded through it. However, if we want to break the Parent Delegation Model, we need to override the `loadClass()` method.

Why does overriding `loadClass()` break the Parent Delegation Model? The execution flow of the Parent Delegation Model already explains it:

> When a ClassLoader performs class loading, it does not try to load the class itself at first; instead, it delegates the request to its parent ClassLoader (by calling the parent's `loadClass()` method).

After overriding `loadClass()`, we can alter the execution flow of the traditional Parent Delegation Model. For example, a child ClassLoader can try to load the class itself before delegating to the parent ClassLoader, or attempt to load from other locations after the parent ClassLoader returns. The exact rules are implemented by us and customized according to project requirements.

A well-known example is the Tomcat server: in order to prioritize loading classes from a Web application's directory before loading classes from other directories, Tomcat defines a custom ClassLoader `WebAppClassLoader` to break the parent delegation mechanism. This is also the exact principle behind class isolation between Web applications under Tomcat.

Tomcat's ClassLoader hierarchy is structured as follows:

![Tomcat ClassLoader hierarchy](/media/jg/ext/oss.javaguide.cn/javaguide/java/jvm/tomcat-class-loader-parents-delegation-model-0938e048.png)

Modern Tomcat uses the `Bootstrap -> System -> Common -> WebappX` hierarchy by default. The search locations of each ClassLoader are as follows:

- `Common`'s search locations are configured by `common.loader` in `$CATALINA_BASE/conf/catalina.properties`, which by default mainly include `$CATALINA_BASE/lib` and `$CATALINA_HOME/lib`.
- Each `WebappX` ClassLoader is responsible for `/WEB-INF/classes` and `/WEB-INF/lib/*.jar` of its corresponding Web application.
- The `Server` and `Shared` ClassLoaders are not defined by default; they only appear in more complex hierarchies if `server.loader` or `shared.loader` is explicitly configured.

From the delegation relationships in the diagram, we can see:

- Classes visible to the `Common` ClassLoader can be shared by Tomcat's internal components and all Web applications.
- When explicitly configured, `Server` is visible only to Tomcat internals, whereas `Shared` is visible to all Web applications. In the default configuration without these two ClassLoaders, Web application ClassLoaders directly use `Common` as their parent ClassLoader.
- Each Web application creates a dedicated `WebAppClassLoader` and sets the Thread Context ClassLoader to `WebAppClassLoader` on the thread that starts the Web application. Each `WebAppClassLoader` instance is isolated from the others, thereby achieving class isolation between Web applications.

Relying solely on custom ClassLoaders cannot satisfy certain scenarios—for example, situations where a higher-level ClassLoader needs to load classes that can only be loaded by a lower-level ClassLoader.

For instance, in SPI (Service Provider Interface), the SPI interface (such as `java.sql.Driver`) is provided by the Java core library and loaded by `BootstrapClassLoader`. Meanwhile, the SPI implementation (such as `com.mysql.cj.jdbc.Driver`) is provided by a third-party vendor and loaded by the Application ClassLoader or a custom ClassLoader. By default, a class and its dependencies are loaded by the same ClassLoader. Therefore, the ClassLoader that loads the SPI interface (`BootstrapClassLoader`) would also be used to load the SPI implementation. Under the Parent Delegation Model, `BootstrapClassLoader` cannot locate the SPI implementation class because it cannot delegate downward to a child ClassLoader to attempt loading.

Note here: after JDK 9+ introduced modularization, the JDBC API was split into the `java.sql` module and is no longer loaded directly by `BootstrapClassLoader`, but instead by `PlatformClassLoader`.

```java
public class ClassLoaderTest {
    public static void main(String[] args) throws ClassNotFoundException {
        Class<?> clazz = Class.forName("java.sql.Driver");
        ClassLoader loader = clazz.getClassLoader();
        System.out.println("Loader for java.sql.Driver: " + loader);

        // Under .jdks/corretto-1.8.0_442/bin/java, outputs: Loader for java.sql.Driver: null

        // Under .jdks/jbr-17.0.12/bin/java, outputs: Loader for java.sql.Driver: jdk.internal.loader.ClassLoaders$PlatformClassLoader@30f39991
    }
}
```

As another example, suppose our project includes Spring JARs that are shared across Web applications and therefore loaded by `SharedClassLoader` (with Tomcat as the Web server). Our project contains business classes that use Spring—for example, implementing Spring interfaces or using Spring annotations. Consequently, the ClassLoader that loads Spring (`SharedClassLoader`) will also be asked to load these business classes. However, the business classes reside in the Web application's directory, which is outside `SharedClassLoader`'s loading paths, so `SharedClassLoader` cannot locate or load them.

How do we solve this problem? This is where the **Thread Context ClassLoader (`ThreadContextClassLoader`)** comes in.

Taking Spring as an example, when Spring needs to load business classes, it does not use its own ClassLoader; instead, it uses the current thread's context ClassLoader. Remember what we mentioned above? Each Web application creates a separate `WebAppClassLoader` and sets the Thread Context ClassLoader to `WebAppClassLoader` in the thread that starts the Web application. This allows a higher-level ClassLoader (`SharedClassLoader`) to leverage a child ClassLoader (`WebAppClassLoader`) to load business classes, breaking Java's standard class loading delegation mechanism and allowing applications to use ClassLoaders in reverse.

The principle of the Thread Context ClassLoader is to store a ClassLoader in thread-private data, bound to the thread, and retrieve it when needed. This ClassLoader is typically set by the application or container (such as Tomcat).

`getContextClassLoader()` and `setContextClassLoader(ClassLoader cl)` in `java.lang.Thread` are used to get and set a thread's context ClassLoader, respectively. If not set via `setContextClassLoader(ClassLoader cl)`, a thread inherits the context ClassLoader of its parent thread.

Spring retrieves the Thread Context ClassLoader as follows:

```java
cl = Thread.currentThread().getContextClassLoader();
```
