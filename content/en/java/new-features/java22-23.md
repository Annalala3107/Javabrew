## JDK 23

### JEP 455: Primitive Types in Patterns, instanceof, and switch (Preview)

Before JEP 455, `instanceof` only supported reference types, and `case` labels in `switch` expressions and statements could only use integer literals, enum constants, and string literals.

In the JEP 455 preview feature, `instanceof` and `switch` gain full support for all primitive types, including `byte`, `short`, `char`, `int`, `long`, `float`, `double`, and `boolean`.

```java
// Traditional approach
if (i >= -128 && i <= 127) {
    byte b = (byte)i;
    ... b ...
}

// Improved using instanceof
if (i instanceof byte b) {
    ... b ...
}

long v = ...;
// Traditional approach
if (v == 1L) {
    // ...
} else if (v == 2L) {
    // ...
} else if (v == 10_000_000_000L) {
    // ...
}

// Using long-type case labels
switch (v) {
    case 1L:
        // ...
        break;
    case 2L:
        // ...
        break;
    case 10_000_000_000L:
        // ...
        break;
    default:
        // ...
}
```

### JEP 466: Class File API (Second Preview)

The Class-File API had its first preview in JDK 22, proposed by [JEP 457](https://openjdk.org/jeps/457).

The goal of the Class-File API is to provide a standardized API for parsing, generating, and transforming Java class files, replacing previous reliance on third-party libraries (such as ASM) for class-file processing.

```java
// Create a ClassFile object, which is the entry point for operating on class files.
ClassFile cf = ClassFile.of();
// Parse the byte array into a ClassModel
ClassModel classModel = cf.parse(bytes);

// Build a new class file, removing all methods starting with "debug"
byte[] newBytes = cf.build(classModel.thisClass().asSymbol(),
        classBuilder -> {
            // Iterate over all class elements
            for (ClassElement ce : classModel) {
                // Check whether it is a method and its method name starts with "debug"
                if (!(ce instanceof MethodModel mm
                        && mm.methodName().stringValue().startsWith("debug"))) {
                    // Add to the new class file
                    classBuilder.with(ce);
                }
            }
        });
```

### JEP 467: Markdown Documentation Comments

Markdown syntax can now be used in JavaDoc documentation comments, replacing the traditional approach that only allowed HTML and JavaDoc tags.

Markdown is more concise and readable, reducing the tedium of writing HTML manually while preserving support for HTML elements and JavaDoc tags. This enhancement aims to make writing and reading API documentation comments easier without affecting how existing comments are interpreted. Markdown offers simplified expressions for common documentation elements (such as paragraphs, lists, links, etc.), improving the maintainability of documentation comments and developer experience.

### JEP 469: Vector API (Eighth Incubator)

Vector computations consist of a sequence of operations on vectors. The Vector API expresses vector computations that reliably compile at runtime to optimal vector instructions on supported CPU architectures, thus achieving performance superior to equivalent scalar computations.

The goal of the Vector API is to give users a concise, easy-to-use, platform-independent way to express a wide range of vector computations.

Here is a simple scalar computation on array elements:

```java
void scalarComputation(float[] a, float[] b, float[] c) {
   for (int i = 0; i < a.length; i++) {
        c[i] = (a[i] * a[i] + b[i] * b[i]) * -1.0f;
   }
}
```

Here is the equivalent vector computation using the Vector API:

```java
static final VectorSpecies<Float> SPECIES = FloatVector.SPECIES_PREFERRED;

void vectorComputation(float[] a, float[] b, float[] c) {
    int i = 0;
    int upperBound = SPECIES.loopBound(a.length);
    for (; i < upperBound; i += SPECIES.length()) {
        // FloatVector va, vb, vc;
        var va = FloatVector.fromArray(SPECIES, a, i);
        var vb = FloatVector.fromArray(SPECIES, b, i);
        var vc = va.mul(va)
                   .add(vb.mul(vb))
                   .neg();
        vc.intoArray(c, i);
    }
    for (; i < a.length; i++) {
        c[i] = (a[i] * a[i] + b[i] * b[i]) * -1.0f;
    }
}
```

### JEP 471: Deprecate the Memory-Access Methods in sun.misc.Unsafe for Removal

JEP 471 proposes deprecating the memory-access methods in `sun.misc.Unsafe`, which will be removed in future releases.

Safe and efficient alternatives already exist for these unsafe methods:

- `java.lang.invoke.VarHandle`: Introduced in JDK 9 (JEP 193), providing a safe and efficient way to manipulate heap memory, including object fields, static fields of classes, and array elements.
- `java.lang.foreign.MemorySegment`: Introduced in JDK 22 (JEP 454), providing a safe and efficient way to access off-heap memory, sometimes working in conjunction with `VarHandle`.

`MemorySegment` is one of the core types of the Foreign Function & Memory API, used for safely accessing on-heap or off-heap memory; `VarHandle` is a standalone standard API that can be used to access fields, array elements, or data according to memory layouts. The Foreign Function & Memory API became a final feature in JDK 22.

```java
import java.lang.foreign.*;
import java.lang.invoke.VarHandle;

// Class that manages an off-heap integer array
class OffHeapIntBuffer {

    // VarHandle for accessing integer elements
    private static final VarHandle ELEM_VH = ValueLayout.JAVA_INT.arrayElementVarHandle();

    // Memory manager
    private final Arena arena;

    // Off-heap memory segment
    private final MemorySegment buffer;

    // Constructor, allocates space for the specified number of integers
    public OffHeapIntBuffer(long size) {
        this.arena  = Arena.ofShared();
        this.buffer = arena.allocate(ValueLayout.JAVA_INT, size);
    }

    // Deallocate memory
    public void deallocate() {
        arena.close();
    }

    // Set the value at the specified index with volatile semantics
    public void setVolatile(long index, int value) {
        ELEM_VH.setVolatile(buffer, 0L, index, value);
    }

    // Initialize elements in the specified range to 0
    public void initialize(long start, long n) {
        buffer.asSlice(ValueLayout.JAVA_INT.byteSize() * start,
                       ValueLayout.JAVA_INT.byteSize() * n)
              .fill((byte) 0);
    }

    // Copy elements in the specified range to a new array
    public int[] copyToNewArray(long start, int n) {
        return buffer.asSlice(ValueLayout.JAVA_INT.byteSize() * start,
                              ValueLayout.JAVA_INT.byteSize() * n)
                     .toArray(ValueLayout.JAVA_INT);
    }
}
```

### JEP 474: ZGC: Generational Mode by Default

The default mode of the Z Garbage Collector (ZGC) is switched to generational mode, and non-generational mode is deprecated with plans for removal in future releases. This is because Generational ZGC is the better choice for most scenarios.

### JEP 476: Module Import Declarations (Preview)

Module import declarations allow concisely importing all exported packages of an entire module in Java code without having to declare package imports one by one. This feature simplifies reusing modular libraries—especially when working with multiple modules—by avoiding large numbers of package import statements, making it easier for developers to access third-party libraries and fundamental Java classes.

This feature is particularly useful for beginners and prototyping because it does not require developers to modularize their own code, while retaining compatibility with traditional import styles, thereby improving development productivity and code readability.

```java
// Import the entire java.base module so developers can directly access classes such as List, Map, and Stream without manually importing each package
import module java.base;

public class Example {
    public static void main(String[] args) {
        String[] fruits = { "apple", "berry", "citrus" };
        Map<String, String> fruitMap = Stream.of(fruits)
            .collect(Collectors.toMap(
                s -> s.toUpperCase().substring(0, 1),
                Function.identity()));

        System.out.println(fruitMap);
    }
}
```

### JEP 477: Unnamed Classes and Instance Main Methods (Third Preview)

This feature mainly simplifies the declaration of the `main` method. For Java beginners, the traditional `main` method declaration introduces too many Java syntax concepts at once, making it harder to get started quickly.

Defining a `main` method before using this feature:

```java
public class HelloWorld {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
```

Defining a `main` method using this new feature:

```java
class HelloWorld {
    void main() {
        System.out.println("Hello, World!");
    }
}
```

Further simplification (unnamed classes allow omitting the class name):

```java
void main() {
   System.out.println("Hello, World!");
}
```

### JEP 480: Structured Concurrency (Third Preview)

Java 19 introduced Structured Concurrency as an incubator API. In JDK 23, the API is in its third preview stage, aiming to simplify multithreaded programming rather than replace `java.util.concurrent`.

Structured concurrency treats multiple tasks running in different threads as a single unit of work, thereby simplifying error handling, improving reliability, and enhancing observability. In other words, structured concurrency preserves the readability, maintainability, and observability of single-threaded code.

The fundamental API of structured concurrency is [`StructuredTaskScope`](https://openjdk.org/jeps/480). `StructuredTaskScope` supports splitting a task into multiple concurrent subtasks that execute in their own threads, and subtasks must complete before the main task continues.

Basic usage of `StructuredTaskScope` is as follows:

```java
    try (var scope = new StructuredTaskScope<Object>()) {
        // Use the fork method to spawn threads to execute subtasks
        Subtask<Integer> subtask1 = scope.fork(task1);
        Subtask<String> subtask2 = scope.fork(task2);
        // Wait for threads to complete
        scope.join();
        // Result handling may include processing or rethrowing exceptions
        ... process results/exceptions ...
    } // close
```

Structured concurrency is well suited for virtual threads, which are lightweight threads implemented by the JDK. Many virtual threads share the same operating system thread, allowing a very large number of virtual threads.

### JEP 481: Scoped Values (Third Preview)

Scoped Values enable sharing immutable data within and across threads and are superior to thread-local variables, especially when using large numbers of virtual threads.

```java
final static ScopedValue<...> V = ScopedValue.newInstance();

// In some method
ScopedValue.where(V, <value>)
           .run(() -> { ... V.get() ... call methods ... });

// In a method called directly or indirectly from the lambda expression
... V.get() ...
```

Scoped values allow safe and efficient data sharing between components in large programs without resorting to method parameters.

### JEP 482: Flexible Constructor Bodies (Second Preview)

This feature was originally proposed in JDK 22 by [JEP 447: Statements before super(...) (Preview)](https://openjdk.org/jeps/447).

Java previously required that a `super(...)` or `this(...)` call appear as the first statement in a constructor. This meant we could not directly initialize fields in a subclass constructor before invoking the superclass constructor.

Flexible constructor bodies solve this problem by allowing statements inside a constructor body before invoking `super(..)` or `this(..)`. These statements can initialize fields, though they cannot reference the instance being constructed. This prevents subclass fields from being uninitialized when a superclass constructor invokes a subclass method, strengthening the reliability of class construction.

This feature removes previous Java syntax restrictions on how constructor code is organized, enabling developers to express constructor behavior more freely and naturally—such as validating parameters, preparing state, and sharing logic directly in the constructor without relying on helper methods or auxiliary constructors—thereby improving code readability and maintainability.

```java
class Person {
    private final String name;
    private int age;

    public Person(String name, int age) {
        if (age < 0) {
            throw new IllegalArgumentException("Age cannot be negative.");
        }
        this.name = name; // Initialize fields before calling the superclass constructor
        this.age = age;
        // ... other initialization code
    }
}

class Employee extends Person {
    private final int employeeId;

    public Employee(String name, int age, int employeeId) {
        this.employeeId = employeeId; // Initialize fields before calling the superclass constructor
        super(name, age); // Call the superclass constructor
        // ... other initialization code
    }
}
```

## JDK 22

### JEP 423: Region Pinning for G1

JEP 423 introduces region pinning in the G1 garbage collector to reduce latency caused by Java Native Interface (JNI) critical regions.

Objects inside JNI critical regions cannot be moved during garbage collection, so G1 previously addressed this by disabling garbage collection, causing thread blocking and severe latency. By introducing region pinning in both G1's old and young generations, G1 can pin the memory regions containing objects in critical regions while continuing to collect unpinned regions, avoiding the need to disable garbage collection altogether. This improvement significantly reduces latency and enhances throughput and stability when interacting with JNI.

### JEP 454: Foreign Function & Memory API

Through this API, Java programs can interoperate with code and data outside the Java runtime. By efficiently invoking foreign functions (code outside the JVM) and safely accessing foreign memory (memory not managed by the JVM), the API allows Java programs to call native libraries and process native data without the hazards and fragility of JNI.

The Foreign Function & Memory API had its first incubator in Java 17 via [JEP 412](https://openjdk.java.net/jeps/412), its second incubator in Java 18 via [JEP 419](https://openjdk.org/jeps/419), its first preview in Java 19 via [JEP 424](https://openjdk.org/jeps/424), its second preview in JDK 20 via [JEP 434](https://openjdk.org/jeps/434), and its third preview in JDK 21 via [JEP 442](https://openjdk.org/jeps/442).

Finally, the feature became a permanent, finalized feature in JDK 22.

I have already covered the Foreign Function & Memory API in detail in [Java 19 New Features Overview](./java19.md), so I will not repeat it here.

### JEP 458: Launch Multi-File Source-Code Programs

Java 11 introduced [JEP 330: Launch Single-File Source-Code Programs](https://openjdk.org/jeps/330), enhancing the `java` launcher so it can directly run a single Java source file. With the command `java HelloWorld.java`, Java implicitly compiles the source code in memory and executes it immediately without generating `.class` files on disk. This simplifies workflows when writing small utility programs or learning Java by eliminating an extra manual compilation step.

Suppose the file `Prog.java` declares two classes:

```java
class Prog {
    public static void main(String[] args) { Helper.run(); }
}

class Helper {
    static void run() { System.out.println("Hello!"); }
}
```

The `java Prog.java` command compiles both classes in memory and executes the `main` method of the first class declared in that file.

One limitation of this approach was that all source code for the program had to reside in a single `.java` file.

[JEP 458: Launch Multi-File Source-Code Programs](https://openjdk.org/jeps/458) extends JEP 330 by allowing programs composed of multiple Java source files to be launched directly without an explicit compilation step.

Suppose a directory contains two Java source files, `Prog.java` and `Helper.java`, each declaring one class:

```java
// Prog.java
class Prog {
    public static void main(String[] args) { Helper.run(); }
}

// Helper.java
class Helper {
    static void run() { System.out.println("Hello!"); }
}
```

When you run `java Prog.java`, the Java launcher compiles and executes the `main` method of class `Prog` in memory. Because the code in `Prog` references class `Helper`, the launcher automatically locates `Helper.java` in the file system, compiles `Helper`, and executes it in memory. This process happens automatically without requiring the developer to explicitly invoke `javac` to compile all source files.

This feature makes the transition from small projects to larger projects smoother, allowing developers to choose when to introduce build tools instead of being forced to set up a complex project structure during rapid iteration. By lifting the single-file limitation, it further streamlines the progression from single-file to multi-file programs, making it especially suitable for prototyping, quick experimentation, and early-stage project exploration.
