### JEP 305: Pattern Matching for instanceof (Preview)

Java 14 introduced pattern matching for `instanceof` as a preview feature (JEP 305).

This feature allows type casting to be performed alongside the `instanceof` check, eliminating the need for an explicit cast. Note: Pattern matching for `instanceof` was in its first preview in Java 14 (JEP 305), its second preview in Java 15 (JEP 375), and finally became a standard feature in Java 16 (JEP 394).

### JEP 358: Helpful NullPointerExceptions

By adding the JVM option `-XX:+ShowCodeDetailsInExceptionMessages`, you can obtain more detailed invocation information in a `NullPointerException`, allowing faster root-cause identification and resolution.

```java
a.b.c.i = 99; // Assume this code throws a NullPointerException
```

Before Java 14:

```java
Exception in thread "main" java.lang.NullPointerException
    at NullPointerExample.main(NullPointerExample.java:5)
```

After Java 14:

```java
 // After adding the flag, the exception clearly states which part was null
Exception in thread "main" java.lang.NullPointerException:
        Cannot read field 'c' because 'a.b' is null.
    at Prog.main(Prog.java:5)
```

### JEP 361: Switch Expressions (Standard)

`switch` expressions, introduced as a preview feature in Java 12, became a standard feature in Java 14—no extra flags are required to enable them, and they can be used directly in JDK 14.

Java 12 introduced lambda-like syntax for the execution block when a `switch` condition matches, removing the need for extra `break` statements, while Java 13 provided `yield` to return a value from within a block.

```java
String result = switch (day) {
            case "M", "W", "F" -> "MWF";
            case "T", "TH", "S" -> "TTS";
            default -> {
                if(day.isEmpty())
                    yield "Please insert a valid day.";
                else
                    yield "Looks like a Sunday.";
            }

        };
System.out.println(result);
```

### JEP 359: Records (Preview)

The `record` keyword simplifies defining **data classes** (Java classes that cannot be modified once instantiated). Using `record` instead of `class` lets you declare only the fields, and automatically obtain accessor methods for those fields as well as `toString()`, `hashCode()`, and `equals()`.

It is similar to defining a class with `class` while using the Lombok plugin with `@Getter`, `@ToString`, and `@EqualsAndHashCode`.

```java
/**
 * This class has two characteristics:
 * 1. All member fields are final
 * 2. All methods consist of the constructor and two field accessors (three in total)
 * A class like this is well suited to be declared with record
 */
final class Rectangle implements Shape {
    final double length;
    final double width;

    public Rectangle(double length, double width) {
        this.length = length;
        this.width = width;
    }

    double length() { return length; }
    double width() { return width; }
}
/**
 * 1. A class declared with record automatically gets the three methods in the class above
 * 2. On top of that, it also comes with equals(), hashCode(), and toString()
 * 3. toString() includes the string representation and name of every member field
 */
record Rectangle(float length, float width) { }
```

### JEP 368: Text Blocks (Second Preview)

In Java 14, Text Blocks remained a preview feature, but introduced two new escape sequences:

- `\`: Indicates a line terminator suppression at the end of a line, introducing no newline character
- `\s`: Represents a single space

```java
String str = "凡心所向，素履所往，生如逆旅，一苇以航。";

String str2 = """
        凡心所向，素履所往， \
        生如逆旅，一苇以航。""";
System.out.println(str2);// Output: 凡心所向，素履所往， 生如逆旅，一苇以航。
String text = """
        java
        c++\sphp
        """;
System.out.println(text);
// Output:
java
c++ php
```

### Other Features

- ZGC, introduced in Java 11 as the next-generation GC algorithm after G1, expanded from Linux-only support to supporting macOS and Windows starting in Java 14 (personally, it feels great to finally try ZGC in everyday development environments, even though G1 is actually sufficient).
- [JEP 363: Remove the CMS Garbage Collector](https://openjdk.org/jeps/363) (removes the CMS garbage collector after a successful run).
- Added the `jpackage` tool, which, in addition to packaging applications as standard JARs, supports platform-specific installers such as `deb` and `rpm` on Linux, and `msi` and `exe` on Windows.

### JEP 379: Shenandoah (Shenandoah GC, Standard)

The Shenandoah garbage collector was introduced as an experimental feature in Java 12, and after several versions of iteration and refinement, finally became a production/standard feature in Java 15.

Shenandoah is a low-latency garbage collector led by Red Hat, with the following primary goals:

- 99.9% of GC pause times under 10 ms
- Pause times independent of heap size
- Support for heaps ranging from hundreds of MBs to several TBs

Unlike G1 and ZGC, Shenandoah uses a concurrent mark-compact algorithm that performs garbage collection without stopping application threads.

To enable Shenandoah GC:

```bash
java -XX:+UseShenandoahGC className
```

### JEP 339: EdDSA (Digital Signature Algorithm)

Added a digital signature algorithm based on the Edwards-Curve Digital Signature Algorithm (EdDSA) offering stronger security and performance.

Although its performance outperforms existing ECDSA implementations, it will not completely replace the existing Elliptic Curve Digital Signature Algorithm (ECDSA) in the JDK.

```java
KeyPairGenerator kpg = KeyPairGenerator.getInstance("Ed25519");
KeyPair kp = kpg.generateKeyPair();

byte[] msg = "test_string".getBytes(StandardCharsets.UTF_8);

Signature sig = Signature.getInstance("Ed25519");
sig.initSign(kp.getPrivate());
sig.update(msg);
byte[] s = sig.sign();

String encodedString = Base64.getEncoder().encodeToString(s);
System.out.println(encodedString);
```

Output:

```plain
0Hc0lxxASZNvS52WsvnncJOH/mlFhnA8Tc6D/k5DtAX5BSsNVjtPF4R4+yMWXVjrvB2mxVXmChIbki6goFBgAg==
```

### JEP 378: Text Blocks (Standard)

In Java 15, Text Blocks finally became a standard feature and no longer require the `--enable-preview` flag to use.

Text Blocks provide a cleaner way to define multi-line strings, making them especially well suited for SQL, JSON, HTML, and similar scenarios.

### JEP 371: Hidden Classes

Hidden classes are designed for frameworks, supporting dynamically generated classes that cannot be used directly by the bytecode of other classes and can only be accessed indirectly at runtime via Reflection.

Key characteristics:

- **Undiscoverable**: Hidden classes cannot be directly depended upon by other classes
- **Short lifecycle**: Typically unloaded once no longer in use
- **Performance optimization**: Provides better performance support for dynamic language runtimes

Use cases:

- Dynamic language runtimes (such as JavaScript, Groovy)
- Bytecode generation frameworks (such as ASM, CGLIB)
- Reflection proxies (such as Dynamic Proxy)

### JEP 360: Sealed Classes (Preview)

**Sealed Classes** are a new preview feature introduced in Java 15.

Before sealed classes, if you wanted to prevent a Java class from being inherited and modified, you could use the `final` keyword on the class. However, that approach was inflexible—it completely closed off all inheritance and extension paths for the class.

Sealed classes restrict which classes may extend or implement them, so that the class can only be inherited by specified classes.

```java
// The abstract class Person only allows Employee and Manager to inherit from it.
public abstract sealed class Person
    permits Employee, Manager {

    //...
}
```

In addition, any class extending a sealed class must itself be declared as `sealed`, `non-sealed`, or `final`.

```java
public final class Employee extends Person {
}

public non-sealed class Manager extends Person {
}
```

![](/media/jg/ext/oss.javaguide.cn/javaguide/image-20210820153955587-6c53e213.png)

If the permitted subclasses and the sealed class are in the same source file, the sealed class can omit the `permits` clause; the Java compiler will scan the source file and add the permitted subclasses for the sealed class at compile time.

### JEP 375: Pattern Matching for instanceof (Second Preview)

Java 15 kept pattern matching for `instanceof` as a preview feature without major adjustments, primarily to gather more usage feedback.

Pattern matching for `instanceof` allows variable binding alongside the type check, avoiding explicit type casts and making code cleaner and safer.

Example:

```java
// Traditional style
if (obj instanceof String) {
    String str = (String) obj;
    System.out.println(str.length());
}

// Pattern matching style
if (obj instanceof String str) {
    System.out.println(str.length());
}
```

### API Enhancements

#### CharSequence Enhancements

Before Java 15, if you wanted to check whether a `StringBuilder`, `StringBuffer`, or `CharBuffer` was empty, you typically had to call `length() == 0`.

The `CharSequence` interface added a default method `isEmpty()` to check whether a character sequence is empty, returning `true` if so.

```java
public interface CharSequence {
  default boolean isEmpty() {
      return this.length() == 0;
  }
}
```

Since `String`, `StringBuilder`, and others all implement this interface, you can now write emptiness checks in a more uniform and semantic way. This is very convenient for writing generic code (handling arbitrary character sequences).

**Note:** Although the `String` class already had an `isEmpty()` method long ago, that was defined by `String` itself; Java 15 lifted this capability up to the interface level.

#### TreeMap Performance Improvements

This is a very substantial optimization. Although methods like `putIfAbsent()` and `compute()` appeared in the `Map` interface back in Java 8, before Java 15 `TreeMap` did not implement them itself and instead relied directly on the `default` implementations from the interface.

**What changed in Java 15**: `TreeMap` specifically overrode the following methods:

- `putIfAbsent()`
- `computeIfAbsent()`
- `computeIfPresent()`
- `compute()`
- `merge()`

**Why override them?**

- **Performance gain**: The interface's default implementations are relatively naive and often require multiple lookups (for instance, first checking whether the key exists, then deciding whether to insert).
- **O(log n) guarantee**: `TreeMap`'s optimized implementations combine lookup and insertion into a single Red-Black Tree traversal, avoiding redundant tree searches and significantly improving execution efficiency when handling large datasets.
