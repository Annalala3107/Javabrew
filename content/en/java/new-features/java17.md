Java 17 (JDK 17) was officially released on September 14, 2021, and is designated by Oracle as a Long-Term Support (LTS) release.

According to Oracle's Java SE Support Roadmap updated in April 2026, Premier Support for Oracle JDK 17 runs through September 2026, and Extended Support runs through September 2029. Free update and commercial support lifecycles vary across different JDK distributions, so production environments should rely on the policy of the actual distribution in use.

![](/media/jg/ext/oss.javaguide.cn/javaguide/java/new-features/4c1611fad59449edbbd6e233690e9fa7-08d369cd.png)

When upgrading from JDK 11 to JDK 17, it is recommended to focus on Sealed Classes, Pattern Matching for `switch`, the new Pseudo-Random Number Generator API, and compatibility changes caused by strong encapsulation of JDK internal APIs. The minimum required Java version for Spring 6.x and Spring Boot 3.x is also Java 17.

## JEP 356: Enhanced Pseudo-Random Number Generators

Before JDK 17, we could generate random numbers using `Random`, `ThreadLocalRandom`, and `SplittableRandom`. However, each of these three classes has limitations and lacks support for common pseudo-random algorithms.

Java 17 adds new interface types and implementations for pseudo-random number generators (PRNGs, also known as deterministic random bit generators), making it easier for developers to use different PRNG algorithms interchangeably in applications.

> A [PRNG](https://ctf-wiki.org/crypto/streamcipher/prng/intro/) is used to generate a sequence of numbers that approximates a sequence of truly random numbers. Generally, a PRNG relies on an initial value, also called a seed, to generate the corresponding pseudo-random sequence. Once the seed is fixed, the random numbers generated by the PRNG are completely deterministic; therefore, the generated sequence is not truly random.

Usage example:

```java
RandomGeneratorFactory<RandomGenerator> l128X256MixRandom = RandomGeneratorFactory.of("L128X256MixRandom");
// Use a timestamp as the random seed
RandomGenerator randomGenerator = l128X256MixRandom.create(System.currentTimeMillis());
// Generate a random number
randomGenerator.nextInt(10);
```

## JEP 398: Deprecate the Applet API for Removal

The Applet API was used to write small Java applications running in web browsers. It became obsolete many years ago, and there is no longer any reason to use it.

The Applet API was marked deprecated in Java 9 ([JEP 289](https://openjdk.java.net/jeps/289)), though not for removal at that time.

## JEP 403: Strongly Encapsulate JDK Internals

JDK 17 further strengthens the encapsulation of JDK internal APIs. Some older frameworks, serialization libraries, bytecode tools, or Java Agents rely on reflective access to JDK internal members and may throw `InaccessibleObjectException` after upgrading, so verifying only that business code compiles is not sufficient.

Before upgrading, you can use `jdeps --jdk-internals` to help locate static dependencies on internal APIs, though it cannot detect all reflective accesses—you still need runtime verification covering application startup, core endpoints, scheduled tasks, and monitoring agents. When incompatibilities are found, you should prioritize upgrading the dependencies or switching to supported public APIs; see the [Oracle JDK 17 Migration Guide](https://docs.oracle.com/en/java/javase/17/migrate/preparing-migration.html) for detailed steps.

**In JDK 17, `--illegal-access=permit` can no longer restore the permissive access behavior of earlier releases.** For dependencies that cannot be upgraded immediately, you can selectively open the required packages based on the exception details using `--add-opens`. For example, the flag below grants code on the classpath deep reflective access to the `java.lang` package of the `java.base` module:

```bash
--add-opens java.base/java.lang=ALL-UNNAMED
```

This is only a compatibility workaround for specific access issues; it should not be used as a universal startup flag across all applications, nor can it resolve all JDK upgrade problems. See [JEP 403](https://openjdk.org/jeps/403) for exact boundaries. If you also plan to switch to ZGC during the upgrade, it is recommended to separate dependency compatibility verification from collector performance benchmarking—see [ZGC Collector](../jvm/jvm-garbage-collection.md#zgc-collector).

## JEP 406: Pattern Matching for switch (Preview)

Just like `instanceof`, `switch` soon gained type-matching with automatic casting as well.

`instanceof` code example:

```java
// Old code
if (o instanceof String) {
    String s = (String)o;
    ... use s ...
}

// New code
if (o instanceof String s) {
    ... use s ...
}
```

`switch` code example:

```java
// Old code
static String formatter(Object o) {
    String formatted = "unknown";
    if (o instanceof Integer i) {
        formatted = String.format("int %d", i);
    } else if (o instanceof Long l) {
        formatted = String.format("long %d", l);
    } else if (o instanceof Double d) {
        formatted = String.format("double %f", d);
    } else if (o instanceof String s) {
        formatted = String.format("String %s", s);
    }
    return formatted;
}

// New code
static String formatterPatternSwitch(Object o) {
    return switch (o) {
        case Integer i -> String.format("int %d", i);
        case Long l    -> String.format("long %d", l);
        case Double d  -> String.format("double %f", d);
        case String s  -> String.format("String %s", s);
        default        -> o.toString();
    };
}

```

Handling of `null` values has also been improved.

```java
// Old code
static void testFooBar(String s) {
    if (s == null) {
        System.out.println("oops!");
        return;
    }
    switch (s) {
        case "Foo", "Bar" -> System.out.println("Great");
        default           -> System.out.println("Ok");
    }
}

// New code
static void testFooBar(String s) {
    switch (s) {
        case null         -> System.out.println("Oops");
        case "Foo", "Bar" -> System.out.println("Great");
        default           -> System.out.println("Ok");
    }
}
```

## JEP 407: Remove RMI Activation

Removes the Remote Method Invocation (RMI) Activation mechanism while retaining the rest of RMI. RMI Activation is obsolete and no longer used.

## JEP 409: Sealed Classes

Sealed classes were first proposed for preview in [JEP 360](https://openjdk.java.net/jeps/360) and integrated into Java 15. In JDK 16, sealed classes were refined (with stricter reference checks and inheritance rules for sealed classes) and proposed for a second preview in [JEP 397](https://openjdk.java.net/jeps/397).

I have already covered sealed classes in detail in [Java 14 & 15 New Features Overview](./java14-15.md), so I will not repeat the explanation here.

## JEP 410: Remove the Experimental AOT and JIT Compiler

In Java 9 ([JEP 295](https://openjdk.java.net/jeps/295)), an experimental Ahead-of-Time (AOT) compiler was introduced to compile Java classes to native code before launching the virtual machine.

In Java 17, the experimental Ahead-of-Time (AOT) and Just-in-Time (JIT) compiler was removed because it had seen little use since its introduction and required significant effort to maintain. The experimental Java-level JVM Compiler Interface (JVMCI) is retained so developers can continue using externally built versions of the compiler for JIT compilation.

## JEP 411: Deprecate the Security Manager for Removal

Deprecates the Security Manager for removal in a future release.

The Security Manager dates back to Java 1.0. For many years, it has not been the primary means of securing client-side Java code, and it has rarely been used to secure server-side code. To move Java forward, Java 17 deprecates the Security Manager so it can be removed together with the legacy Applet API ([JEP 398](https://openjdk.java.net/jeps/398)).

## JEP 412: Foreign Function & Memory API (Incubator)

Java programs can use this API to interoperate with code and data outside the Java runtime. By efficiently invoking foreign functions (code outside the JVM) and safely accessing foreign memory (memory not managed by the JVM), this API enables Java programs to call native libraries and process native data without the hazards and fragility of JNI.

The Foreign Function & Memory API underwent its first incubation in Java 17 via [JEP 412](https://openjdk.java.net/jeps/412). Its second incubation was proposed by [JEP 419](https://openjdk.org/jeps/419) and integrated into Java 18, and its preview was proposed by [JEP 424](https://openjdk.org/jeps/424) and integrated into Java 19.

I have already covered the Foreign Function & Memory API in detail in [Java 19 New Features Overview](./java19.md), so I will not repeat the explanation here.

## JEP 414: Vector API (Second Incubator)

The Vector API was first proposed by [JEP 338](https://openjdk.java.net/jeps/338) and integrated into Java 16 as an [Incubator API](http://openjdk.java.net/jeps/11). The second round of incubation was proposed by [JEP 414](https://openjdk.java.net/jeps/414) and integrated into Java 17; the third round was proposed by [JEP 417](https://openjdk.java.net/jeps/417) and integrated into Java 18; and the fourth round was proposed by [JEP 426](https://openjdk.java.net/jeps/426) and integrated into Java 19.

This incubator API provides an initial iteration of an API for expressing vector computations that reliably compile at runtime to optimal vector hardware instructions on supported CPU architectures, thereby achieving better performance than equivalent scalar computations by taking full advantage of Single Instruction, Multiple Data (SIMD) technology (an instruction capability available on most modern CPUs). Although HotSpot supports auto-vectorization, the set of scalar operations that can be transformed is limited and fragile with respect to code changes. This API enables developers to easily write portable, high-performance vector algorithms in Java.

I have already covered the Vector API in detail in [Java 18 New Features Overview](./java18.md), so I will not repeat the explanation here.
