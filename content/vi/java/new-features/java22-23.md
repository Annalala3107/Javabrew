## JDK 23

### JEP 455: Kiểu nguyên thủy trong Pattern, instanceof và switch (Bản xem trước)

Trước JEP 455, `instanceof` chỉ hỗ trợ kiểu tham chiếu, còn nhãn `case` của biểu thức và câu lệnh `switch` chỉ có thể dùng literal số nguyên, hằng số enum và literal chuỗi.

Trong tính năng xem trước của JEP 455, `instanceof` và `switch` hỗ trợ toàn diện tất cả các kiểu nguyên thủy, bao gồm `byte`, `short`, `char`, `int`, `long`, `float`, `double`, `boolean`.

```java
// Cách viết truyền thống
if (i >= -128 && i <= 127) {
    byte b = (byte)i;
    ... b ...
}

// Cải tiến bằng instanceof
if (i instanceof byte b) {
    ... b ...
}

long v = ...;
// Cách viết truyền thống
if (v == 1L) {
    // ...
} else if (v == 2L) {
    // ...
} else if (v == 10_000_000_000L) {
    // ...
}

// Sử dụng nhãn case kiểu long
switch (v) {
    case 1L:
        // ...
        break;
    case 2L:
        // ...
        break;
    case 10_000_000_000L:
        // ...
        break;
    default:
        // ...
}
```

### JEP 466: Class File API (Bản xem trước lần 2)

Class File API đã được xem trước lần đầu trong JDK 22 do [JEP 457](https://openjdk.org/jeps/457) đề xuất.

Mục tiêu của Class File API là cung cấp một bộ API tiêu chuẩn để phân tích cú pháp, tạo mới và chuyển đổi tệp class Java, thay thế sự phụ thuộc trước đây vào các thư viện bên thứ ba (như ASM) khi xử lý tệp class.

```java
// Tạo một đối tượng ClassFile, đây là điểm vào để thao tác với tệp class.
ClassFile cf = ClassFile.of();
// Phân tích mảng byte thành ClassModel
ClassModel classModel = cf.parse(bytes);

// Xây dựng tệp class mới, loại bỏ tất cả phương thức bắt đầu bằng "debug"
byte[] newBytes = cf.build(classModel.thisClass().asSymbol(),
        classBuilder -> {
            // Duyệt qua tất cả các phần tử của lớp
            for (ClassElement ce : classModel) {
                // Kiểm tra xem có phải là phương thức và tên phương thức bắt đầu bằng "debug" hay không
                if (!(ce instanceof MethodModel mm
                        && mm.methodName().stringValue().startsWith("debug"))) {
                    // Thêm vào tệp class mới
                    classBuilder.with(ce);
                }
            }
        });
```

### JEP 469: Vector API (Thử nghiệm lần 8)

Tính toán vector bao gồm một chuỗi các phép toán trên vector. Vector API được dùng để biểu diễn các phép tính vector có thể được biên dịch một cách tin cậy tại runtime thành các lệnh vector tối ưu nhất trên các kiến trúc CPU được hỗ trợ, qua đó đạt hiệu năng vượt trội so với tính toán vô hướng (scalar) tương đương.

Mục tiêu của Vector API là mang đến cho người dùng cách thức ngắn gọn, dễ dùng và độc lập nền tảng để biểu diễn đa dạng các phép tính vector.

Đây là phép tính vô hướng đơn giản trên các phần tử mảng:

```java
void scalarComputation(float[] a, float[] b, float[] c) {
   for (int i = 0; i < a.length; i++) {
        c[i] = (a[i] * a[i] + b[i] * b[i]) * -1.0f;
   }
}
```

Đây là phép tính vector tương đương sử dụng Vector API:

```java
static final VectorSpecies<Float> SPECIES = FloatVector.SPECIES_PREFERRED;

void vectorComputation(float[] a, float[] b, float[] c) {
    int i = 0;
    int upperBound = SPECIES.loopBound(a.length);
    for (; i < upperBound; i += SPECIES.length()) {
        // FloatVector va, vb, vc;
        var va = FloatVector.fromArray(SPECIES, a, i);
        var vb = FloatVector.fromArray(SPECIES, b, i);
        var vc = va.mul(va)
                   .add(vb.mul(vb))
                   .neg();
        vc.intoArray(c, i);
    }
    for (; i < a.length; i++) {
        c[i] = (a[i] * a[i] + b[i] * b[i]) * -1.0f;
    }
}
```

### JEP 471: Đánh dấu lỗi thời các phương thức truy cập bộ nhớ trong sun.misc.Unsafe

JEP 471 đề xuất đánh dấu lỗi thời (`deprecate`) các phương thức truy cập bộ nhớ trong `sun.misc.Unsafe`; các phương thức này sẽ bị loại bỏ trong các phiên bản tương lai.

Những phương thức không an toàn này đã có các giải pháp thay thế an toàn và hiệu quả:

- `java.lang.invoke.VarHandle`: Được giới thiệu trong JDK 9 (JEP 193), cung cấp phương thức an toàn và hiệu quả để thao tác với bộ nhớ Heap, bao gồm các trường của đối tượng, trường tĩnh (`static`) của lớp và các phần tử mảng.
- `java.lang.foreign.MemorySegment`: Được giới thiệu trong JDK 22 (JEP 454), cung cấp phương thức an toàn và hiệu quả để truy cập bộ nhớ ngoài Heap (off-heap), đôi khi phối hợp làm việc cùng `VarHandle`.

`MemorySegment` là một trong những kiểu cốt lõi của Foreign Function & Memory API (API Hàm ngoài & Bộ nhớ ngoài), dùng để truy cập an toàn bộ nhớ trong Heap hoặc ngoài Heap; còn `VarHandle` là API chuẩn độc lập có thể dùng để truy cập trường, phần tử mảng hoặc truy cập dữ liệu theo bố cục bộ nhớ. Foreign Function & Memory API đã trở thành tính năng chính thức từ JDK 22.

```java
import java.lang.foreign.*;
import java.lang.invoke.VarHandle;

// Lớp quản lý mảng số nguyên ngoài Heap
class OffHeapIntBuffer {

    // VarHandle dùng để truy cập các phần tử kiểu số nguyên
    private static final VarHandle ELEM_VH = ValueLayout.JAVA_INT.arrayElementVarHandle();

    // Trình quản lý bộ nhớ
    private final Arena arena;

    // Phân đoạn bộ nhớ ngoài Heap
    private final MemorySegment buffer;

    // Hàm khởi tạo, cấp phát không gian cho số lượng số nguyên chỉ định
    public OffHeapIntBuffer(long size) {
        this.arena  = Arena.ofShared();
        this.buffer = arena.allocate(ValueLayout.JAVA_INT, size);
    }

    // Giải phóng bộ nhớ
    public void deallocate() {
        arena.close();
    }

    // Thiết lập giá trị tại chỉ mục chỉ định theo ngữ nghĩa volatile
    public void setVolatile(long index, int value) {
        ELEM_VH.setVolatile(buffer, 0L, index, value);
    }

    // Khởi tạo giá trị 0 cho phạm vi phần tử chỉ định
    public void initialize(long start, long n) {
        buffer.asSlice(ValueLayout.JAVA_INT.byteSize() * start,
                       ValueLayout.JAVA_INT.byteSize() * n)
              .fill((byte) 0);
    }

    // Sao chép các phần tử trong phạm vi chỉ định sang một mảng mới
    public int[] copyToNewArray(long start, int n) {
        return buffer.asSlice(ValueLayout.JAVA_INT.byteSize() * start,
                              ValueLayout.JAVA_INT.byteSize() * n)
                     .toArray(ValueLayout.JAVA_INT);
    }
}
```

### JEP 474: ZGC: Chế độ phân thế hệ mặc định

Chế độ mặc định của bộ thu gom rác Z Garbage Collector (ZGC) được chuyển sang chế độ phân thế hệ (Generational Mode), đồng thời đánh dấu lỗi thời chế độ không phân thế hệ với kế hoạch loại bỏ ở các phiên bản sau. Lý do là vì Generational ZGC là lựa chọn tối ưu hơn trong hầu hết các kịch bản.

### JEP 476: Khai báo nhập module (Bản xem trước)

Khai báo nhập module (`import module`) cho phép nhập gọn toàn bộ các gói (package) được export của một module ngay trong mã Java mà không cần khai báo `import` từng gói riêng lẻ. Tính năng này đơn giản hóa việc tái sử dụng các thư viện theo module, đặc biệt khi dùng nhiều module cùng lúc, tránh phải viết hàng loạt câu lệnh `import` gói, giúp lập trình viên truy cập thuận tiện hơn vào thư viện bên thứ ba và các lớp cơ bản của Java.

Tính năng này đặc biệt hữu ích cho người mới bắt đầu và giai đoạn dựng nguyên mẫu (prototyping), vì nó không yêu cầu lập trình viên phải module hóa mã nguồn của chính mình, đồng thời vẫn duy trì khả năng tương thích với cách `import` truyền thống, giúp nâng cao hiệu suất phát triển và tính dễ đọc của mã nguồn.

```java
// Nhập toàn bộ module java.base, lập trình viên có thể truy cập trực tiếp các lớp như List, Map, Stream mà không cần import thủ công từng gói liên quan
import module java.base;

public class Example {
    public static void main(String[] args) {
        String[] fruits = { "apple", "berry", "citrus" };
        Map<String, String> fruitMap = Stream.of(fruits)
            .collect(Collectors.toMap(
                s -> s.toUpperCase().substring(0, 1),
                Function.identity()));

        System.out.println(fruitMap);
    }
}
```

### JEP 477: Lớp không tên và phương thức main thể hiện (Bản xem trước lần 3)

Tính năng này chủ yếu đơn giản hóa việc khai báo phương thức `main`. Đối với người mới học Java, cách khai báo phương thức `main` truyền thống đưa vào quá nhiều khái niệm cú pháp Java, gây khó khăn cho việc tiếp cận nhanh.

Định nghĩa phương thức `main` trước khi sử dụng tính năng này:

```java
public class HelloWorld {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
```

Định nghĩa phương thức `main` sau khi sử dụng tính năng mới:

```java
class HelloWorld {
    void main() {
        System.out.println("Hello, World!");
    }
}
```

Đơn giản hóa hơn nữa (lớp không tên cho phép chúng ta lược bỏ tên lớp):

```java
void main() {
   System.out.println("Hello, World!");
}
```

### JEP 480: Structured Concurrency (Bản xem trước lần 3)

Java 19 đã giới thiệu Structured Concurrency (lập trình đồng thời có cấu trúc) dưới dạng API thử nghiệm (incubator). Trong JDK 23, API này đang ở giai đoạn xem trước lần thứ ba, với mục đích đơn giản hóa lập trình đa luồng (multithreaded programming) chứ không nhằm thay thế `java.util.concurrent`.

Structured Concurrency coi nhiều tác vụ chạy trên các Thread khác nhau như một đơn vị công việc duy nhất, qua đó đơn giản hóa xử lý lỗi, nâng cao độ tin cậy và tăng cường khả năng quan sát (observability). Nói cách khác, Structured Concurrency giữ lại tính dễ đọc, dễ bảo trì và dễ quan sát như mã nguồn đơn luồng.

API cơ bản của Structured Concurrency là [`StructuredTaskScope`](https://openjdk.org/jeps/480). `StructuredTaskScope` hỗ trợ chia tách một tác vụ thành nhiều tác vụ con đồng thời chạy trên các Thread riêng của chúng, và các tác vụ con phải hoàn thành trước khi tác vụ chính tiếp tục.

Cách dùng cơ bản của `StructuredTaskScope` như sau:

```java
    try (var scope = new StructuredTaskScope<Object>()) {
        // Dùng phương thức fork để tạo luồng thực thi tác vụ con
        Subtask<Integer> subtask1 = scope.fork(task1);
        Subtask<String> subtask2 = scope.fork(task2);
        // Đợi các luồng hoàn thành
        scope.join();
        // Việc xử lý kết quả có thể bao gồm xử lý hoặc ném lại ngoại lệ
        ... process results/exceptions ...
    } // close
```

Structured Concurrency đặc biệt phù hợp với Virtual Thread (luồng ảo), vốn là loại Thread nhẹ do JDK cài đặt. Nhiều Virtual Thread dùng chung một Thread hệ điều hành, từ đó cho phép tồn tại số lượng cực lớn Virtual Thread.

### JEP 481: Scoped Values (Bản xem trước lần 3)

Scoped Values (giá trị theo phạm vi) cho phép chia sẻ dữ liệu bất biến bên trong một Thread và giữa các Thread với nhau, ưu việt hơn biến cục bộ theo luồng (`ThreadLocal`), đặc biệt là khi sử dụng số lượng lớn Virtual Thread.

```java
final static ScopedValue<...> V = ScopedValue.newInstance();

// Trong một phương thức nào đó
ScopedValue.where(V, <value>)
           .run(() -> { ... V.get() ... call methods ... });

// Trong một phương thức được gọi trực tiếp hoặc gián tiếp từ biểu thức lambda
... V.get() ...
```

Scoped Values cho phép chia sẻ dữ liệu an toàn và hiệu quả giữa các thành phần trong các chương trình lớn mà không cần phải truyền qua tham số phương thức.

### JEP 482: Thân hàm khởi tạo linh hoạt (Bản xem trước lần 2)

Tính năng này ban đầu được đề xuất trong JDK 22 bởi [JEP 447: Statements before super(...) (Preview)](https://openjdk.org/jeps/447).

Trước đây, Java yêu cầu lời gọi `super(...)` hoặc `this(...)` trong constructor phải xuất hiện dưới dạng câu lệnh đầu tiên. Điều này khiến chúng ta không thể khởi tạo trực tiếp các trường trong constructor của lớp con trước khi gọi constructor của lớp cha.

Thân hàm khởi tạo linh hoạt (Flexible Constructor Bodies) giải quyết vấn đề này bằng cách cho phép viết các câu lệnh bên trong thân constructor trước khi gọi `super(..)` hoặc `this(..)`. Các câu lệnh này có thể khởi tạo trường nhưng không được tham chiếu tới thực thể đang được khởi tạo. Cách làm này ngăn tình trạng trường của lớp con chưa được khởi tạo đúng cách khi constructor của lớp cha gọi tới phương thức của lớp con, nâng cao độ tin cậy khi khởi tạo lớp.

Tính năng này giải quyết hạn chế cú pháp trước đây của Java đối với cách tổ chức mã trong constructor, giúp lập trình viên thể hiện hành vi constructor một cách tự do và tự nhiên hơn — ví dụ thực hiện kiểm tra tham số, chuẩn bị và chia sẻ dữ liệu trực tiếp ngay trong constructor mà không cần phụ thuộc vào phương thức bổ trợ hay constructor phụ, từ đó cải thiện tính dễ đọc và khả năng bảo trì mã nguồn.

```java
class Person {
    private final String name;
    private int age;

    public Person(String name, int age) {
        if (age < 0) {
            throw new IllegalArgumentException("Age cannot be negative.");
        }
        this.name = name; // Khởi tạo trường trước khi gọi constructor lớp cha
        this.age = age;
        // ... các đoạn mã khởi tạo khác
    }
}

class Employee extends Person {
    private final int employeeId;

    public Employee(String name, int age, int employeeId) {
        this.employeeId = employeeId; // Khởi tạo trường trước khi gọi constructor lớp cha
        super(name, age); // Gọi constructor lớp cha
        // ... các đoạn mã khởi tạo khác
    }
}
```

## JDK 22

### JEP 423: Cố định vùng nhớ (Region Pinning) cho G1 Garbage Collector

JEP 423 đề xuất triển khai tính năng cố định vùng nhớ (Region Pinning) trong G1 Garbage Collector nhằm giảm độ trễ phát sinh do các vùng tới hạn của Java Native Interface (JNI).

Các đối tượng bên trong vùng tới hạn JNI không thể bị di chuyển trong quá trình Garbage Collection, do đó trước đây G1 xử lý bằng cách vô hiệu hóa Garbage Collection, dẫn đến tình trạng nghẽn Thread và độ trễ nghiêm trọng. Nhờ đưa cơ chế Region Pinning vào cả thế hệ già (Old Generation) và thế hệ trẻ (Young Generation) của G1, bộ thu gom có thể cố định riêng vùng nhớ chứa các đối tượng nằm trong vùng tới hạn, đồng thời vẫn tiếp tục thu gom các vùng không bị cố định, tránh được việc phải tắt hẳn Garbage Collection. Cải tiến này giúp giảm đáng kể độ trễ, nâng cao thông lượng (throughput) và tính ổn định của hệ thống khi tương tác với JNI.

### JEP 454: Foreign Function & Memory API

Thông qua API này, các chương trình Java có thể tương tác với mã nguồn và dữ liệu bên ngoài môi trường chạy Java (Java runtime). Bằng cách gọi hiệu quả các hàm ngoài (tức mã nằm ngoài JVM) và truy cập an toàn vùng nhớ ngoài (tức vùng nhớ không do JVM quản lý), API này giúp chương trình Java gọi được các thư viện native và xử lý dữ liệu native mà không gặp rủi ro và sự mong manh như JNI.

Foreign Function & Memory API đã trải qua vòng thử nghiệm đầu tiên trong Java 17 do [JEP 412](https://openjdk.java.net/jeps/412) đề xuất, thử nghiệm lần hai trong Java 18 bởi [JEP 419](https://openjdk.org/jeps/419), xem trước lần đầu trong Java 19 bởi [JEP 424](https://openjdk.org/jeps/424), xem trước lần hai trong JDK 20 bởi [JEP 434](https://openjdk.org/jeps/434) và xem trước lần ba trong JDK 21 bởi [JEP 442](https://openjdk.org/jeps/442).

Cuối cùng, tính năng này đã chính thức hoàn thiện trong JDK 22.

Trong bài [Tổng quan các tính năng mới của Java 19](./java19.md), tôi đã giới thiệu chi tiết về Foreign Function & Memory API nên sẽ không trình bày lại ở đây nữa.

### JEP 456: Biến và mẫu không tên (Unnamed Variables & Patterns)

Biến và mẫu không tên đã được xem trước trong JDK 21 qua [JEP 443](https://openjdk.org/jeps/443) và chính thức hoàn thiện trong JDK 22.

Để xem giới thiệu chi tiết về tính năng mới này, bạn có thể tham khảo bài viết [Tổng quan các tính năng mới của Java 21 (Quan trọng)](./java21.md).

### JEP 458: Khởi chạy chương trình mã nguồn nhiều tệp

Java 11 đã giới thiệu [JEP 330: Launch Single-File Source-Code Programs (Khởi chạy chương trình mã nguồn một tệp)](https://openjdk.org/jeps/330), tăng cường khả năng cho trình khởi chạy `java` để chạy trực tiếp một tệp mã nguồn Java duy nhất. Với lệnh `java HelloWorld.java`, Java có thể biên dịch ngầm mã nguồn trong bộ nhớ và thực thi ngay lập tức mà không cần tạo tệp `.class` trên đĩa. Điều này giúp đơn giản hóa quy trình làm việc của lập trình viên khi viết các công cụ nhỏ hoặc học Java, tránh được bước biên dịch thủ công thừa thãi.

Giả sử tệp `Prog.java` khai báo hai lớp:

```java
class Prog {
    public static void main(String[] args) { Helper.run(); }
}

class Helper {
    static void run() { System.out.println("Hello!"); }
}
```

Lệnh `java Prog.java` sẽ biên dịch cả hai lớp trong bộ nhớ và thực thi phương thức `main` của lớp đầu tiên được khai báo trong tệp đó.

Cách này có một hạn chế là toàn bộ mã nguồn của chương trình phải đặt trong một tệp `.java` duy nhất.

[JEP 458: Launch Multi-File Source-Code Programs (Khởi chạy chương trình mã nguồn nhiều tệp)](https://openjdk.org/jeps/458) là phần mở rộng của JEP 330, cho phép chạy trực tiếp chương trình gồm nhiều tệp mã nguồn Java mà không cần bước biên dịch tường minh.

Giả sử trong một thư mục có hai tệp mã nguồn Java là `Prog.java` và `Helper.java`, mỗi tệp khai báo một lớp riêng:

```java
// Prog.java
class Prog {
    public static void main(String[] args) { Helper.run(); }
}

// Helper.java
class Helper {
    static void run() { System.out.println("Hello!"); }
}
```

Khi bạn chạy lệnh `java Prog.java`, trình khởi chạy Java sẽ biên dịch và thực thi phương thức `main` của lớp `Prog` trong bộ nhớ. Do mã nguồn trong lớp `Prog` có tham chiếu đến lớp `Helper`, trình khởi chạy sẽ tự động tìm kiếm tệp `Helper.java` trong hệ thống tệp, biên dịch lớp `Helper` bên trong và thực thi nó trong bộ nhớ. Quá trình này diễn ra hoàn toàn tự động, lập trình viên không cần gọi tường minh `javac` để biên dịch toàn bộ các tệp mã nguồn.

Tính năng này giúp quá trình chuyển đổi từ dự án nhỏ sang dự án lớn trở nên mượt mà hơn; lập trình viên có thể tự do lựa chọn thời điểm đưa các công cụ build vào sử dụng, tránh bị ép buộc phải thiết lập cấu trúc dự án phức tạp khi đang lặp nhanh. Tính năng này xóa bỏ giới hạn một tệp duy nhất, tiếp tục đơn giản hóa quá trình phát triển từ một tệp sang chương trình nhiều tệp, đặc biệt phù hợp cho dựng nguyên mẫu, thử nghiệm nhanh và giai đoạn khám phá ban đầu của dự án.
