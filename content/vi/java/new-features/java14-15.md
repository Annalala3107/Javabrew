## Java 14

JDK 14 được phát hành vào ngày 17/03/2020, đây là một phiên bản không phải LTS (non-LTS).

Bài viết này sẽ chọn lọc và giới thiệu chi tiết một số tính năng mới tương đối quan trọng trong đó:

- [JEP 305: Pattern Matching for instanceof (Pattern Matching cho instanceof, xem trước)](https://openjdk.org/jeps/305)
- [JEP 358: Helpful NullPointerExceptions (Thông báo chính xác lỗi NullPointerException)](https://openjdk.org/jeps/358)
- [JEP 361: Switch Expressions (Standard) (Biểu thức switch, chính thức)](https://openjdk.org/jeps/361)
- [JEP 359: Records (Preview) (Từ khóa record, tính năng xem trước)](https://openjdk.org/jeps/359)
- [JEP 368: Text Blocks (Second Preview) (Khối văn bản, xem trước lần hai)](https://openjdk.org/jeps/368)
- [JEP 363: Remove the CMS Garbage Collector (Loại bỏ bộ thu gom rác CMS)](https://openjdk.org/jeps/363)

Biểu đồ dưới đây thể hiện số lượng tính năng mới và thời gian phát hành của từng phiên bản từ JDK 8 đến JDK 25:

### JEP 305: Pattern Matching for instanceof (Pattern Matching cho instanceof, xem trước)

Java 14 đưa Pattern Matching cho `instanceof` vào làm tính năng xem trước; đây là tính năng được giới thiệu trong Java 14 (JEP 305).

Tính năng này cho phép thực hiện ép kiểu đồng thời ngay trong lúc kiểm tra `instanceof`, tránh phải viết ép kiểu tường minh. Lưu ý: Pattern Matching cho `instanceof` được xem trước lần đầu ở Java 14 (JEP 305), xem trước lần hai ở Java 15 (JEP 375), và cuối cùng trở thành tính năng chính thức ở Java 16 (JEP 394).

### JEP 358: Helpful NullPointerExceptions (Thông báo chính xác lỗi NullPointerException)

Thông qua việc thêm tham số JVM `-XX:+ShowCodeDetailsInExceptionMessages`, bạn có thể nhận được thông tin lời gọi chi tiết hơn trong `NullPointerException`, giúp định vị và xử lý lỗi nhanh hơn.

```java
a.b.c.i = 99; // Giả sử đoạn code này xảy ra NullPointerException
```

Trước Java 14:

```java
Exception in thread "main" java.lang.NullPointerException
    at NullPointerExample.main(NullPointerExample.java:5)
```

Từ Java 14 trở đi:

```java
 // Sau khi thêm tham số, thông báo ngoại lệ chỉ rõ chính xác vị trí nào bị null
Exception in thread "main" java.lang.NullPointerException:
        Cannot read field 'c' because 'a.b' is null.
    at Prog.main(Prog.java:5)
```

### JEP 361: Switch Expressions (Biểu thức switch, bản chuẩn)

Biểu thức `switch` được giới thiệu từ Java 12 (dạng tính năng xem trước) đã trở thành phiên bản chính thức trong Java 14, không cần thêm tham số để bật nữa mà có thể dùng trực tiếp trong JDK 14.

Java 12 đã đưa vào cú pháp tương tự lambda cho khối thực thi sau khi khớp điều kiện trong biểu thức `switch` để không cần viết nhiều `break`, còn Java 13 cung cấp `yield` để trả về giá trị bên trong block.

```java
String result = switch (day) {
            case "M", "W", "F" -> "MWF";
            case "T", "TH", "S" -> "TTS";
            default -> {
                if(day.isEmpty())
                    yield "Please insert a valid day.";
                else
                    yield "Looks like a Sunday.";
            }

        };
System.out.println(result);
```

### JEP 359: Records (Lớp record, xem trước)

Từ khóa `record` có thể đơn giản hóa cách định nghĩa **lớp dữ liệu (data class)** (một lớp Java một khi đã khởi tạo thì không thể sửa đổi nữa). Dùng `record` thay cho `class` để định nghĩa lớp thì chỉ cần khai báo thuộc tính là có thể tự động có các phương thức truy cập thuộc tính, cùng với `toString()`, `hashCode()` và `equals()`.

Tương tự như việc định nghĩa lớp bằng `class` kết hợp sử dụng plugin Lombok và gắn các annotation `@Getter`, `@ToString`, `@EqualsAndHashCode`.

```java
/**
 * Lớp này có hai đặc điểm:
 * 1. Mọi thuộc tính thành viên đều là final
 * 2. Toàn bộ phương thức gồm constructor và hai phương thức truy cập thuộc tính thành viên (tổng cộng 3 phương thức)
 * Những lớp như vậy rất phù hợp để khai báo bằng record
 */
final class Rectangle implements Shape {
    final double length;
    final double width;

    public Rectangle(double length, double width) {
        this.length = length;
        this.width = width;
    }

    double length() { return length; }
    double width() { return width; }
}
/**
 * 1. Lớp khai báo bằng record sẽ tự động có 3 phương thức như lớp trên
 * 2. Ngoài ra còn được tặng kèm phương thức equals(), hashCode() và toString()
 * 3. Phương thức toString() bao gồm biểu diễn chuỗi và tên của tất cả các thuộc tính thành viên
 */
record Rectangle(float length, float width) { }
```

### JEP 368: Text Blocks (Khối văn bản, xem trước lần hai)

Trong Java 14, Text Blocks vẫn là tính năng xem trước, tuy nhiên nó đã bổ sung hai ký tự escape mới:

- `\`: Biểu thị ở cuối dòng, không chèn ký tự xuống dòng
- `\s`: Biểu thị một khoảng trắng đơn

```java
String str = "凡心所向，素履所往，生如逆旅，一苇以航。";

String str2 = """
        凡心所向，素履所往， \
        生如逆旅，一苇以航。""";
System.out.println(str2);// Kết quả: 凡心所向，素履所往， 生如逆旅，一苇以航。
String text = """
        java
        c++\sphp
        """;
System.out.println(text);
// Kết quả:
java
c++ php
```

### Các tính năng khác

- ZGC được giới thiệu từ Java 11 với tư cách là thuật toán GC thế hệ tiếp theo sau G1: từ việc chỉ hỗ trợ nền tảng Linux, bắt đầu từ Java 14 đã hỗ trợ macOS và Windows (cảm nhận cá nhân là cuối cùng cũng có thể trải nghiệm thử hiệu quả của ZGC ngay trên công cụ lập trình hằng ngày, dù thực ra G1 cũng đã đủ dùng).
- [JEP 363: Remove the CMS Garbage Collector](https://openjdk.org/jeps/363) (loại bỏ bộ thu gom rác CMS sau khi hoàn thành sứ mệnh).
- Bổ sung công cụ `jpackage`, ngoài việc đóng gói ứng dụng thành file JAR tiêu chuẩn còn hỗ trợ đóng gói theo định dạng đặc thù của từng nền tảng, như `deb` và `rpm` trên Linux, hay `msi` và `exe` trên nền tảng Windows.

### JEP 379: Shenandoah (Shenandoah GC, bản chuẩn)

Bộ thu gom rác Shenandoah bắt đầu được đưa vào dưới dạng tính năng thử nghiệm từ Java 12, trải qua nhiều phiên bản cải tiến và hoàn thiện, cuối cùng đã trở thành tính năng chính thức trong Java 15.

Shenandoah là bộ thu gom rác độ trễ thấp do Red Hat dẫn đầu phát triển, với các mục tiêu chính:

- 99.9% thời gian tạm dừng GC nhỏ hơn 10ms
- Thời gian tạm dừng không phụ thuộc vào kích thước Heap
- Hỗ trợ bộ nhớ Heap từ vài trăm MB đến vài TB

Khác với G1 và ZGC, Shenandoah áp dụng thuật toán đánh dấu-dồn nén đồng thời (concurrent mark-compact), có thể thu gom rác mà không cần dừng các Thread ứng dụng.

Kích hoạt Shenandoah GC:

```bash
java -XX:+UseShenandoahGC className
```

### JEP 339: EdDSA (Thuật toán chữ ký số)

Bổ sung một thuật toán chữ ký số dựa trên Edwards-Curve Digital Signature Algorithm (EdDSA) có tính bảo mật và hiệu năng mạnh mẽ hơn.

Mặc dù hiệu năng của nó vượt trội hơn bản cài đặt ECDSA hiện có, nhưng nó sẽ không thay thế hoàn toàn thuật toán chữ ký số đường cong Elliptic (ECDSA) hiện tại trong JDK.

```java
KeyPairGenerator kpg = KeyPairGenerator.getInstance("Ed25519");
KeyPair kp = kpg.generateKeyPair();

byte[] msg = "test_string".getBytes(StandardCharsets.UTF_8);

Signature sig = Signature.getInstance("Ed25519");
sig.initSign(kp.getPrivate());
sig.update(msg);
byte[] s = sig.sign();

String encodedString = Base64.getEncoder().encodeToString(s);
System.out.println(encodedString);
```

Kết quả đầu ra:

```plain
0Hc0lxxASZNvS52WsvnncJOH/mlFhnA8Tc6D/k5DtAX5BSsNVjtPF4R4+yMWXVjrvB2mxVXmChIbki6goFBgAg==
```

### JEP 378: Text Blocks (Khối văn bản, bản chuẩn)

Ở Java 15, Text Blocks cuối cùng cũng trở thành tính năng chính thức, không còn cần tham số `--enable-preview` vẫn có thể sử dụng được.

Text Blocks cung cấp một cách gọn gàng hơn để định nghĩa chuỗi nhiều dòng, đặc biệt phù hợp cho các kịch bản như SQL, JSON, HTML, v.v.

### JEP 371: Hidden Classes (Lớp ẩn)

Hidden Classes (lớp ẩn) được thiết kế dành cho các framework, hỗ trợ các lớp được tạo động mà bytecode của những lớp khác không thể sử dụng trực tiếp, chỉ có thể sử dụng gián tiếp thông qua Reflection tại runtime.

Đặc điểm chính:

- Không thể bị phát hiện: Lớp ẩn không thể bị các lớp khác phụ thuộc trực tiếp
- Vòng đời ngắn: Thường sẽ bị dỡ bỏ (unload) sau khi sử dụng xong
- Tối ưu hiệu năng: Hỗ trợ hiệu năng tốt hơn cho runtime của các ngôn ngữ động

Kịch bản áp dụng:

- Runtime của ngôn ngữ động (như JavaScript, Groovy)
- Framework sinh bytecode (như ASM, CGLIB)
- Reflection Proxy (như Dynamic Proxy)

### JEP 360: Sealed Classes (Lớp niêm phong, xem trước)

**Sealed Classes (Lớp niêm phong)** là một tính năng mới dạng xem trước trong Java 15.

Trước khi có Sealed Classes, trong Java nếu muốn một lớp không thể bị kế thừa và sửa đổi, ta có thể dùng từ khóa `final` để bổ nghĩa cho lớp đó. Tuy nhiên, cách này không linh hoạt vì chặn đứng hoàn toàn mọi con đường kế thừa và mở rộng của lớp.

Sealed Classes có thể giới hạn những lớp nào được phép kế thừa hoặc triển khai chúng, nhờ vậy lớp này chỉ có thể được kế thừa bởi các lớp được chỉ định.

```java
// Lớp trừu tượng Person chỉ cho phép Employee và Manager kế thừa.
public abstract sealed class Person
    permits Employee, Manager {

    //...
}
```

Ngoài ra, bất kỳ lớp nào kế thừa một lớp `sealed` bản thân nó cũng phải được khai báo là `sealed`, `non-sealed` hoặc `final`.

```java
public final class Employee extends Person {
}

public non-sealed class Manager extends Person {
}
```

![](/media/jg/ext/oss.javaguide.cn/javaguide/image-20210820153955587-6c53e213.png)

Nếu các lớp con được phép mở rộng và lớp niêm phong nằm trong cùng một file mã nguồn, lớp niêm phong có thể không cần dùng mệnh đề `permits`; trình biên dịch Java sẽ quét file mã nguồn và tự động bổ sung các lớp con được cấp phép cho lớp niêm phong tại thời điểm biên dịch.

### JEP 375: Pattern Matching for instanceof (Pattern Matching cho instanceof, xem trước lần hai)

Java 15 tiếp tục giữ Pattern Matching cho `instanceof` làm tính năng xem trước mà không có điều chỉnh lớn nào, chủ yếu nhằm thu thập thêm phản hồi sử dụng.

Pattern Matching cho `instanceof` cho phép gán biến ngay trong lúc kiểm tra kiểu, tránh ép kiểu tường minh, giúp code ngắn gọn và an toàn hơn.

Ví dụ:

```java
// Cách viết truyền thống
if (obj instanceof String) {
    String str = (String) obj;
    System.out.println(str.length());
}

// Cách viết Pattern Matching
if (obj instanceof String str) {
    System.out.println(str.length());
}
```

### Cải tiến API

#### Cải tiến CharSequence

Trước Java 15, nếu muốn kiểm tra xem một `StringBuilder`, `StringBuffer` hay `CharBuffer` có rỗng hay không, bạn thường phải gọi `length() == 0`.

Interface `CharSequence` đã bổ sung một phương thức mặc định `isEmpty()` để kiểm tra chuỗi ký tự có rỗng hay không, trả về `true` nếu rỗng.

```java
public interface CharSequence {
  default boolean isEmpty() {
      return this.length() == 0;
  }
}
```

Do `String`, `StringBuilder`, v.v. đều cài đặt interface này, giờ đây bạn có thể viết logic kiểm tra theo cách thống nhất và giàu ngữ nghĩa hơn. Điều này rất thân thiện khi viết code Generics (xử lý nhiều loại chuỗi ký tự khác nhau).

**Lưu ý:** Dù lớp `String` đã có sẵn phương thức `isEmpty()` từ lâu, nhưng đó là phương thức do chính `String` tự định nghĩa; bước đi này ở Java 15 đã "đẩy" năng lực đó lên tầng interface.

#### Nâng cao hiệu năng TreeMap

Đây là một tối ưu rất đáng giá ở tầng dưới. Mặc dù các phương thức như `putIfAbsent()`, `compute()` đã xuất hiện trong interface `Map` từ Java 8, nhưng trước Java 15, `TreeMap` không tự cài đặt lại chúng mà dùng thẳng các cài đặt `default` trong interface.

**Thay đổi ở Java 15**: `TreeMap` đã ghi đè (`Override`) chuyên biệt các phương thức sau:

- `putIfAbsent()`
- `computeIfAbsent()`
- `computeIfPresent()`
- `compute()`
- `merge()`

**Tại sao phải ghi đè?**

- **Nâng cao hiệu năng**: Các cài đặt mặc định trong interface thường khá "thô", hay phải thực hiện nhiều lần tìm kiếm (ví dụ kiểm tra tồn tại trước rồi mới quyết định có chèn hay không).
- **Đảm bảo O(log n)**: Cài đặt được tối ưu của `TreeMap` có thể gộp việc tìm kiếm và chèn vào trong một lần duyệt cây đỏ-đen (Red-Black Tree) duy nhất, tránh việc tìm kiếm trên cây lặp đi lặp lại, cải thiện rõ rệt hiệu quả thực thi khi xử lý dữ liệu quy mô lớn.
